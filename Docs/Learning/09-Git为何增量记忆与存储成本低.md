# 09 · Git 为何能「增量记忆」、存储成本为什么低

> **结论先行**：Git 不是每次提交都整仓复印一份；它按**内容哈希**存「独一无二的文件快照块」，提交之间**共享未改动的对象**，长期再用 **pack**（打包文件）做压缩与相似块去重。所以历史可以很长，磁盘却常常远小于「提交次数 × 工作区体积」。

## 1. 「增量记忆」到底记的是什么

口语里的「增量」容易误会成「只存 diff 补丁链」。Git 的心智更接近：

```text
每次 commit ≈ 给「当时整棵目录树」拍一张逻辑快照
但物理上：未改动的文件 = 复用同一个对象；只为改动的文件新建对象
```

| 术语 | 是什么 | 起什么作用 |
|---|---|---|
| **对象库** `.git/objects` | Git 存放所有不可变数据块的地方 | 历史、文件、目录结构都在这里 |
| **内容寻址** | 用内容的哈希当地址/文件名 | 相同内容只存一份；改一字节就换新地址 |
| **blob** | 一个文件内容的对象（不含路径名） | 「这份字节」的唯一存档 |
| **tree** | 一目录：名字 → 子 tree / blob 的清单 | 拼出某一刻的文件夹结构 |
| **commit** | 元数据 + 指向某棵根 tree + 父 commit | 「这一刀历史」：谁、何时、说明、基于谁 |

因此：**逻辑上每次提交都是完整快照**（检出任意旧 commit 不需要重放一百条补丁）；**物理上大量复用**未变 blob/tree。这就是「增量记忆」在 Git 里的真义——**共享不变部分**，不是「只会存 diff、离开链条就拼不出全文」。

## 2. 为什么改一行不会复制整个项目

假设工作区有 1000 个文件，你只改了 `network_p2.rs` 并 commit：

```text
commit N+1
  └─ tree（根）── 可能是新 tree（因为子项哈希变了）
        ├─ src-tauri/src/tree … 沿路径上的 tree 可能各新一份
        │     └─ blob(network_p2.rs)  ← 新内容，新哈希，新对象
        ├─ Docs/... 等 ← 仍指向**旧 blob**（哈希不变则对象不变）
        └─ …
```

| 发生了什么 | 存储含义 |
|---|---|
| 未改文件 | **零字节新增**（指针仍指向旧 blob） |
| 改了的文件 | 新增 **一个** blob（整文件一版内容；见下节「整文件」） |
| 路径上的目录 | 可能新增少量 tree（目录清单变了） |
| commit 本身 | 很小的元数据对象 |

所以成本近似随「**改动触及的内容**」增长，而不是随「仓库总文件数 × 提交次数」线性爆炸。

**边界**：单次 commit 里，Git 对每个改动文件存的是该文件的**完整一版内容**（blob），不是「相对上一版只存那一行 diff」。增量感来自**跨提交共享未改文件**，不是单文件内只存行 diff（行 diff 是 `git diff` 给人看的视图）。

## 3. 内容哈希：相同即同一份

**哈希**（hash，散列）是什么：把任意长度内容映射成固定长度指纹（Git 用 SHA-1；迁移 SHA-256 在推进）。起什么作用：指纹当对象 ID——内容一样 → ID 一样 → 磁盘上只留一份。

后果：

1. **跨目录、跨提交去重**：两个路径若文件字节完全相同，可共用一个 blob。  
2. **完整性**：对象名绑死内容；悄悄改字节会对不上 ID。  
3. **分布式友好**：两台机器算出同一 blob ID，即可认定内容相同，便于推送时只传缺失对象。

## 4. 长期为何还更省：pack 文件

松散对象（每个对象一个小文件）多了以后，Git 会打成 **packfile**（打包文件）：

| 机制 | 是什么 | 起什么作用 |
|---|---|---|
| **pack** | 多个对象打成少数大文件 | 减少 inode/小文件开销；便于传输 |
| **delta 压缩** | pack 内对**相似对象**存「相对某基对象的差异」 | 同一文件多版本、相近大文件时显著省空间 |
| **zlib 等压缩** | 对象/ pack 再压缩 | 文本类源码压缩比通常很好 |

`git gc`（垃圾回收与优化）会触发打包、丢掉不可达对象。你平时感觉「仓库没那么大」，常有 pack 的功劳。

**边界**：极端情况仍可能很大——反复提交巨型二进制、不该进库的 `target/` / 视频、或历史里删不掉的大文件（要从历史上 purge 才真正瘦身）。源码仓「便宜」不等于「随便塞二进制也便宜」。

## 5. 和「每次整仓备份」比成本

| 方式 | 10 次提交、每次只改 1 个小文件 | 粗直觉 |
|---|---|---|
| 每次复制整个工作区 | ≈ 10 × 全仓体积 | 贵 |
| Git（共享 blob + 少量新 tree/commit） | ≈ 1 × 全仓（首份）+ 10 ×（小文件新版本 + 元数据） | 低 |
| Git + pack delta | 多版本相近文件再压一层 | 往往更低 |

「存储成本低」是相对「快照次数 × 全量拷贝」而言；首份完整内容仍要存一次。

## 6. 一张总图

```text
commit  ← 小：说明 + 父指针 + 根 tree ID
  │
  tree  ← 中小：文件名列表 → 子 ID（未改子树可共用旧 tree）
  │
  blob  ← 文件全文一版；相同全文全仓唯一

跨 commit：未改 blob/tree 直接共用箭头
长期：许多对象打进 pack，相似 blob 再 delta
```

## 7. 和本仓日常的对应（建议心智）

| 你做的事 | 对象层发生什么 |
|---|---|
| 只改 `Docs/Learning/09-….md` 并 commit | 新 blob（该 md）+ 沿路径新 tree + 新 commit；代码 blob 全共用 |
| `git add` 再改又 `add` | 暂存区换钉住的 blob 候选；commit 只封最后钉住的那版 |
| clone / fetch | 主要拉**缺失对象**（及 pack），不是每次整仓 tar |

相关命令（观察用，非必须）：

```bash
# 看仓库对象大致体积
git count-objects -vH

# 某次提交根树
git rev-parse HEAD^{tree}

# 某文件在 tip 的 blob id（内容指纹）
git hash-object -w --stdin < 某文件   # 勿随便 -w；只读可用 hash-object 无 -w
git ls-tree HEAD -- path/to/file
```

## 8. 常见误解

| 误解 | 更正 |
|---|---|
| Git 历史 = 一长串 patch，离开就拼不出文件 | 逻辑是快照；patch 是显示/传输时的视图 |
| 每次 commit 磁盘 +整仓 | 只为变化的内容（及路径上的 tree）付费 |
| 仓库永远很小 | 大二进制、误提交构建产物会很贵 |
| `commit -a` 更省空间 | 省的是键盘，不是对象模型；存什么仍取决于内容是否变化 |
