# 启动与测试相关概念

> 读完能看懂 [04-启动与测试](../04-启动与测试.md) 里每一句在说什么、为何要这样验。  
> 产品机制见 [01-核心逻辑](../01-核心逻辑.md)；模块落点见 [02-项目架构](../02-项目架构.md)。

## 1. 结论

本仓是 **CCM→Tauri 迁移仓**（是什么：把原 Electron 壳上的配置管理器迁到 Tauri 的工作仓库；起什么作用：日常路径纯 Rust，未迁能力以 stub 明示）。日常开发要同时理解三条线：

1. **壳 + UI**：Tauri 窗口 + Vite 前端  
2. **已迁业务**：Rust 分域（Deploy / Scan MVP / Projects / refresh / 迁入备份等）  
3. **未迁业务**：全盘发现 / Config 为 Bridge stub（默认不启 sidecar；可选旁路联调）

读 04 时的口诀：**冒烟绿 ≠ 手测绿；体积数字勿混比口径；日常无 Node ≠ 全盘发现已迁。**（**已验证**：04 与 Plan/02 对「发行未打入 sidecar / stub」一致。）

## 2. 运行时拓扑（读命令前先看）

结论：`tauri:dev` 不是「只起一个窗口」，而是一条开发栈。

```text
浏览器式 UI (Vite :1420)
        │
        ▼
  ccmBridge（按 method 分流）
     ├──► Rust（日常主路径）
     ├──► stub（全盘发现 / Config）
     └──► Node sidecar (:17832)  ← 仅 VITE_CCM_USE_SIDECAR=1 可选旁路
        │
Tauri 壳（WebView2 里嵌上述 UI）
```

| 角色 | 是什么 | 起什么作用 |
|------|--------|------------|
| **Tauri** | 用系统 WebView 托管前端、用 Rust 写本机能力的桌面框架 | 提供窗口与本机 API，替代 Electron 主进程壳 |
| **WebView2** | Windows 上的嵌入式浏览器控件 | 真正渲染 React UI |
| **Vite** | 前端开发服务器与打包器 | 开发期在 `:1420` 热更新 UI |
| **Node sidecar** | 随开发栈拉起的本地 Node 进程，托管原 Electron `AppController`（是什么：原主进程业务控制器；起什么作用：集中处理 IPC 请求） | 迁移期补齐尚未写成 Rust 的 IPC |
| **IPC** | Inter-Process Communication，进程间通信 | UI 用统一方法名调本机能力，不关心背后是 Rust 还是 sidecar |
| **Bridge**（`ccmBridge`） | 前端侧按 method 分流的适配层 | 已迁走 Rust，未迁走 sidecar |

## 3. 产品域概念（04 冒烟标题在验什么）

结论：04 里的「域 N / refresh / backup」是**迁移切片名**，对应产品动作，不是无关测试名。

| 04 用语 | 是什么 | 起什么作用 | 今日归属（**已验证**·对照 02） |
|---------|--------|------------|-------------------------------|
| **Deploy / Withdraw** | 放入容器 / 移出或存回 | 库正本 ↔ 生效位置之间的复制与冲突决议 | Rust 域3 |
| **Scan / Ingest MVP** | 扫描登记 + 纳入台账的最小可用版 | 把磁盘上的配置记进永久库账本 | Rust 域4（活动容器 + 库磁盘 add；**全盘发现未迁**） |
| **永久库** | 本机停用仓库与内容权威源 | 在此不生效，只作定稿与台账 | 产品核心；迁入目标 |
| **活动容器 / spike 活动容器** | 工具正在读的配置目录；spike 指本仓对照用的实验容器范围 | 放这里才对 Cursor 等工具生效 | 域4/refresh 边界用语 |
| **Projects / Purpose** | 项目条目与用途/标签等元数据 | 按项目组织与检索配置资产 | Rust 域5 MVP；Config **未迁** stub |
| **refresh / 对账** | 拿容器存活副本与库正本比对 | 发现漂移与冲突并支持决议（如 overwrite） | Rust refresh |
| **迁入备份** | 把容器侧副本迁入永久库的流程 | 去副本、统一权威源 | Rust `backup` |
| **双份对比**（dual copy） | 同名两份内容并排查看 | 冲突时人眼定稿 | Rust `dual_copy` / `getDualCopyTexts` |
| **全盘发现**（ProjectDiscovery） | 跨盘扫描找项目/配置根 | 建库时的广覆盖入口 | **未迁**（Bridge stub；App 无入口） |
| **Config** | 应用级配置读写（非台账本身） | 目录模式等五件套 | **未迁**（Bridge stub；App 无入口） |

产品硬边界（与启动无关但读冒烟必须懂）：**库 ≠ 生效**；**同名 ≠ 同版**（看哈希）。

## 4. 迁移与阶段用语

结论：04 开头的「迁移仓 / 过渡期 / M1 厚路径」决定你该不该指望「无 Node 也能全功能」。

| 用语 | 是什么 | 起什么作用 |
|------|--------|------------|
| **迁移仓** | 本仓库相对 Electron 主仓的角色定位 | 允许边用 sidecar 边退役，而不是一次重写 |
| **Electron 主仓** | `E:\Code\CursorConfigManager` 产品自用线 | 对照与兜底；本仓失败不得停更主仓 |
| **闸门 / 纯 Rust 闸门 exe** | 迁仓前用小体积 Rust 壳做的可行性对照物 | 证明壳可行；**体积不可与「含 Node 过渡发行」混比** |
| **M0 / M1 / M3** | 迁移里程碑编号 | M0 通 sidecar；M1 厚路径手测；M3 分域迁 Rust、终态退役 sidecar |
| **厚路径** | 仍依赖 sidecar 的完整业务调用链 | `verify:sidecar` 验的是这条链还活着 |
| **MVP** | Minimum Viable Product，最小可用实现 | 冒烟绿只保证切片内场景，不保证全盘/全历史行为 |
| **SSOT** | Single Source of Truth，单一事实来源 | IPC 契约以 `shared/ipc.ts` 对齐前后端，避免各写各的 |

## 5. 命令与端口（概念层）

结论：04 的脚本分四类——**起栈 / 拆栈 / 冒烟 / 发行**；端口冲突多半是旧栈没退。

| 概念 | 是什么 | 起什么作用 |
|------|--------|------------|
| `npm install` | 按 `package.json` 装 Node 依赖 | 首次或依赖变更后才能跑脚本 |
| `tauri:dev` | 开发态启动 Tauri | 默认只起 Vite `:1420`（无 sidecar）；可选 `tauri:dev:sidecar` |
| `sidecar` / `dev:tauri-ui` | 只起 Node 侧 / 只起 UI | 排障或可选联调 |
| **`:1420` / `:17832`** | 本机 TCP 端口 | UI 与 sidecar 的固定约会点；占用则新进程起不来 |
| `tauri:build` | 打开发行用二进制（本仓默认 `--no-bundle`） | 产出可分发壳；**默认未打入 Node sidecar**（**已验证**·04） |
| `cargo test --lib` | 只跑 Rust 库单测 | 不经过 npm 冒烟脚本，直接验 Rust 逻辑 |
| `ensure-electron` + `dev:electron` | 可选拉起本仓内 Electron 对照 | 与主仓 `npm run dev` 不同路径，勿混 |

「Node sidecar 未就绪」：仅 `VITE_CCM_USE_SIDECAR=1` 且打到未迁 method 时需要；日常路径不依赖（**已验证**·02/04）。

## 6. 验证概念：冒烟 vs 单测 vs 验收

结论：04 大量 `verify:*` 是**自动化冒烟**，不是产品完整验收。

| 用语 | 是什么 | 起什么作用 | 边界 |
|------|--------|------------|------|
| **冒烟**（smoke） | 最短路径探活：关键入口还能通 | 改架构后快速发现「整段断了」 | 不替代手测与边界用例 |
| `verify:sidecar` | 对 sidecar IPC 的冒烟 | 确认厚路径未静默死亡 | 需先 `npm run sidecar` |
| `verify:rust-domain*` / `refresh` / `backup` | 对已迁 Rust 域的脚本化检查（底层常跑 cargo） | 分域回归，数字如「27/31 passed」是切片内断言数 | 绿 ≠ 全盘发现已迁 |
| **冲突决议**（overwrite / skip / conflict） | 双份内容不一致时的策略枚举 | 自动化与 UI 共用同一套语义 | 人选策略仍要人点 |
| **验收步骤** | 人按清单点 UI 的确认 | 证明「用户路径」可用 | 04 侧重命令；手测清单在 Plan/状态里演进 |
| **allow-pick-folder** | Tauri 能力白名单里的选目录权限名 | 未声明则 `pick_folder` 无反应 | 属壳安全模型，不是业务 bug |

## 7. 发行口径（为何 04 强调「勿混比」）

结论：两个体积数字回答的是**两个不同问题**。

| 口径 | 回答的问题 | 典型数字/状态 |
|------|------------|----------------|
| 历史纯 Rust 闸门 | 「空壳+少量 Rust 能力有多瘦？」 | ≈5.68 MB（**已验证**·P3；无 sidecar） |
| 本仓日常发行 | 「默认包有没有 Node？」 | **无 Node**（**已验证**·04）；全盘发现/Config 未做 |

日常路径可无 sidecar。**建议**：对外说「日常无 Node」，勿称「与 Electron 全盘发现对等」。

## 8. 对照主仓时要想什么

结论：主仓是产品真源自用线；本仓是换壳迁移实验线。

| 现象（04 FAQ） | 概念解释 |
|----------------|----------|
| 扫描很慢 | 「扫描建库」MVP 只扫活动容器 + 库磁盘；非全盘多盘 walk |
| 选文件夹无反应 | 壳权限 / 命令未暴露，先查 allowlist，再查 UI 是否调了 `pick_folder` |
| 端口占用 | 旧 `tauri:dev` / sidecar / Vite 残留；结束占用进程或依赖 stack 复用健康实例 |

## 9. 记忆链

```text
04 在教你三件事：
  怎么起（tauri:dev 默认无 sidecar；可选 sidecar 联调）
  → 怎么验（verify:no-sidecar + 分域 Rust；可选 verify:sidecar）
  → 怎么发（build 默认无 Node；全盘发现未做）

读标题时翻译：
  域3 = 放入/移出
  域4 = 扫描纳入（MVP，非全盘）
  域5 = 项目/用途
  refresh = 对账
  backup/dual = 迁入与双份对比
  stub = 全盘发现 + Config（App 无入口）
```
