## 经验条目

### 漏斗标注冻容器态 + 切货架丢池

- **日期**：2026-08-19
- **症状 / 背景**：网络条目转入**永久库**（库存正本）再部署进当前**容器**（工作区里实际生效的配置目录）后，下部同名行不变绿，上窗右键仍是永久库菜单。切走「网络 / 筛选」再切回，货架要重新铺**漏斗池**（当前筛选用的条目数组）才亮。点大人群档整窗假死数秒。
- **走过的弯路**：
  1. **漏斗标注缓存**（按条目 id 记住人群分类、避免每帧重算的 Map）为了叠容器标志，命中后**整对象克隆**。`isInContainerList` / `isInActiveUse` 冻在「未部署」那一版；列表也丢了引用相等，缓存命中仍约 63 ms（对照原先约 14 ms）。
  2. 离开网络/筛选时 `setFunnelPool([])`，以为能省内存。再打开必须重铺整份网络索引。
  3. 点人群档同步跑 **功能桶扫描**（`partitionRefine`：按路径/域把剩余列表切成互斥芯片）。合成 4000 条约 4 s，挡住第一帧出表。
- **最终正确做法**（合成基准 + 单测 **已验证**；人手 GUI **待验证**；数字见 [04](04-启动与测试.md)）：
  - 缓存只复用人群字段，容器态跟当前快照；同标志返回同一对象。本地上窗右键按所在窗口固定为容器菜单。
  - 切走网络/筛选不清漏斗池；条目引用相同则保留原数组。索引/开关变了才重建。
  - 点档先按人群过滤出表（热中位 **0.76 ms**）；功能桶扫描放到空闲后再填芯片。算法本身未改，仍约 4 s。
- **关键文件**：`src/lib/funnelAnnotateCache.ts`、`src/App.tsx`、`scripts/bench-persona.mjs`
- **禁止再犯**：禁止把容器/在用标志写进「只按 id 永不过期」的整对象缓存；禁止用清空漏斗池当「离开货架的清理」；禁止让 `partitionRefine` 挡住第一帧出表。

### 打开本地存放目录落到「文档」（explorer 丢参数）

- **日期**：2026-08-16
- **症状 / 背景**：网络工作台右键「打开本地存放目录」多次失败：无窗口、报错，或弹出用户「文档」文件夹，而不是该条在网络库里的缓存目录（如 `C:\CursorSkills\.net\cache\…`）。
- **走过的弯路**：
  1. 用 `explorer /select,目录`「定位」技能夹。Windows 上对目录经常无窗口、也无报错。
  2. 改成 `open_path` 直接打开目录后一度可用。
  3. 「打开文件夹提速」给**所有** Windows `spawn` 加了 **CREATE_NO_WINDOW**（创建无窗口：专给控制台进程藏黑窗）+ **DETACHED_PROCESS**（分离进程：不挂在 CCM 下）。资源管理器是 GUI，藏窗旗标会把文件夹窗口藏掉。
  4. 去掉藏窗旗标后仍 spawn `explorer.exe <路径>`。已打开的 Explorer 通过 DDE 接管新进程时**丢掉文件夹参数**，落到默认的「文档」。
- **最终正确做法**（路径规范化单测 **已验证**；人手 GUI **待验证**）：
  - 目录 / URL：Windows **ShellExecuteW「open」**（系统「打开」动作，直接交给壳），不要 spawn explorer。
  - 路径去掉 `\\?\`、正斜杠改反斜杠，否则壳也会解析失败。
  - 打开类 IPC 仍不回全量快照。
- **关键文件**：
  - `src-tauri/src/shell_ops.rs` — `shell_execute_open` / `windows_shell_path`
  - `src-tauri/src/network_library.rs` — `open_network_entry_dir` 只 `open_path` 该条缓存目录
- **禁止再犯**：禁止 spawn `explorer.exe` 来打开目录；禁止对 explorer 加 CREATE_NO_WINDOW / DETACHED_PROCESS；改「打开变快」时先确认人手点本菜单落到 **cache 下该技能夹**，而不是「文档」。

### fetch 失败一律删缓存 + 根目录 SKILL.md 当 0 条

- **日期**：2026-08-13
- **症状 / 背景**：侧栏拉 MetaGPT 报 `sslv3 alert handshake failure` 且「已尝试重建缓存仍失败」；langchain 警告「已缓存但 0 个条目」；部分仓（如 blader/humanizer）GitHub 上明明有 `SKILL.md`（Agent Skill 清单文件，供代理加载工作流），中间窗口却显示「未发现可入库」。
- **走过的弯路**：
  1. 把 **TLS**（Transport Layer Security，传输加密）握手失败当成缓存损坏：`shallow_clone_or_update_with` 对 Healthy 仓 fetch 失败一律 `force_remove_dir_all` 再克隆。网络抖动时先毁掉可用缓存，重克隆再因同一 SSL 失败 → 条目消失、中间窗口变空。
  2. 发现只认「子目录内含 SKILL.md」，仓库根部的清单文件被跳过；E011 把 humanizer 归进「无技能文件」是同一误判。
- **最终正确做法**（读码 + 单测 + `verify-tauri` 静态防回归 **已验证**；人手 GUI **待验证**）：
  1. `is_transient_network_error` 识别 `unable to access` / handshake / 超时 / 连接重置等；Healthy 仓遇网络类错误 **保留缓存**，报「已保留本地缓存，条目仍可用」；仅非网络类（仓损坏）才强删重建。
  2. 缓存根含 `SKILL.md` → 整仓记为 1 条 skill（显示名取 `owner/repo` 的仓名）；稀疏展开加 `/**` 检出附属文件。`copy_tree` 本就会跳过 `.git`。
  3. 确证无清单或 404 的精选源退役（langchain / MetaGPT / llama_index / dspy / stagehand / Awesome 空仓 / 404），**保留** `blader-humanizer`。
- **关键文件**：`src-tauri/src/network_library.rs`、`src-tauri/src/network_catalog.rs`、`src/components/NetworkShelf.tsx`、`scripts/verify-tauri.mjs`。

### 大仓拉取失败：先当超时，实测是 Windows Filename too long

- **日期**：2026-08-13
- **症状 / 背景**：侧栏拉 AutoGPT / langchain / MetaGPT / llama_index 后中间窗口空白、无「已缓存」徽标；打开缓存目录像没反应。小仓正常。
- **走过的弯路**：按「数百 MB + 300 秒无 git 进度硬杀」推断超时；未先对一个代表仓跑完整克隆拿错误原文。代表仓实测 **18 s** 即失败，原文是 checkout `Filename too long`（Windows 传统 260 字符路径上限），半成品被清、索引不登记。侧栏「已缓存」只读索引 `sources[]`，与空磁盘脱节。
- **最终正确做法**（`probe_sources` 真实拉取 + `verify:tauri` 204 测 **已验证**；人手 GUI **待验证**）：
  1. **部分克隆**：`--filter=blob:none --depth 1 --no-checkout`，再 sparse `--no-cone` 检出 `**/SKILL.md` `**/*.mdc`，发现后把整个技能目录加入稀疏集。
  2. Git 低于 2.25 或任一 sparse 步骤失败 → 自动回退全量浅克隆；两条路径都带 `core.longpaths=true`。
  3. 取证用 `CCM_FORCE_FULL_SHALLOW=1` 强制旧路径。
  4. 徽标改为索引且磁盘 `Healthy`；失败原因进中间窗口空态带重试。
- **关键文件**：`src-tauri/src/network_library.rs`、`src-tauri/src/network_catalog.rs`、`src-tauri/examples/probe_sources.rs`、`src/components/NetworkShelf.tsx`、`src/App.tsx`。

### 网络条目禁用 Crepe 治闪烁：零高度自毁 + ResizeObserver 重试成环

- **日期**：2026-08-12
- **症状 / 背景**：点网络条目打开详情时整窗闪烁。**Crepe**（Milkdown 开箱即用的所见即所得 Markdown 编辑器，本仓详情页签用它渲染/编辑正文）在创建后若测到宿主 `clientHeight === 0` 会自毁并报 `size` 失败；**ResizeObserver**（监听元素尺寸变化的浏览器 API）见有尺寸又再创建，于是「建→测 0→毁→建」可循环。未就绪时 fallback `<pre>` 盖满编辑区，视觉上就是整窗闪。
- **走过的弯路**：按条目类型禁用渲染器——网络条目强制走「代码」纯文本（后端 `summary` 升 `raw`、前端 `openNetworkDoc` 再 `setDetailMode('raw')`、页签 effect 对 `net:` 早退）。闪烁停了，但用户看不到渲染后的 Markdown，也无法方便复制。
- **最终正确做法**（读码 + 单测 + 静态防回归 **已验证**；人手 GUI 无闪烁/划选复制 **待验证**）：
  1. 网络条目与本地条目同一套 Markdown 页签；`editable=false`（快照已把 `canSaveDetailMarkdown` 置 false），禁止保存、关工具栏。
  2. **安全阀**：同一次挂载内 `size` 失败自动重试不超过 `SIZE_RETRY_MAX`（3 次）；超限停在失败横幅 + 「重试」按钮，最坏退化为可读可复制的 `<pre>`，不可能无限循环。
  3. **remount 去抖**：空/空白正文不覆盖已有页签、不递增 `remountKey`（页签重挂载计数：一变就整组件销毁重建，是唯一完整重建路径）。
  4. 文档条提供「复制全文」（Markdown 原文）与「复制纯文本」（渲染后可见文字）；局部复制靠原生划选 + Ctrl+C。
  5. 防回归：`verify-tauri.mjs` 禁止 snapshot/`openNetworkDoc` 再把网络条目升 `raw`，并要求 `SIZE_RETRY_MAX` 与 `detail-md-copy`。
- **关键文件**：`src-tauri/src/snapshot.rs`、`src/App.tsx`、`src/components/DetailMarkdownCrepe.tsx`、`scripts/verify-tauri.mjs`。

### 半成品 `.git` 被当有效缓存 + Windows 只读 pack 让清理静默失败

- **日期**：2026-08-12
- **症状 / 背景**：侧栏对 `github/awesome-copilot` 等源「拉取当前源」反复失败；无「已缓存」徽标、右键「打开源缓存目录」灰显。磁盘有 `cache/<id>/.git`（含 `shallow.lock`、只读 `tmp_pack_*`）但无工作树；该 id 也不在 `network-index.json` 的 `sources[]`。
- **走过的弯路**：只怀疑网络/代理；未先对照「磁盘缓存目录数 vs 索引 sources 数」，也未检查半成品 `.git` 是否让重拉走错分支。
- **最终正确做法**（读码 + 磁盘实证 + `verify:tauri` 196 测 + 静态防回归 **已验证**；人手重拉 awesome-copilot **待验证**）：
  1. **三段叠加**：拉取硬超时/取消杀 git → cleanup 见 `.git` 就当有效缓存不删 → Windows 上 pack 只读使 `remove_dir_all` 失败被 `let _` 吞掉 → 下次走 `fetch`，`shallow.lock` 直接失败且 fetch 分支无失败清理。
  2. `cached_repo_state`：无 index / 有 `*.lock` / HEAD 不可解析 → `Broken`；Broken 先 `force_remove_dir_all`（递归清只读）再全新 clone。Healthy 的 fetch 失败：**仅非网络类**才自愈重克隆（2026-08-13 更正，见上条「fetch 失败一律删缓存」）。
  3. job 清理与「清理无效缓存」统一走 `force_remove_dir_all`。
  4. 防回归：`verify-tauri.mjs` 要求源码含 `force_remove_dir_all` / `cached_repo_state`。
- **关键文件**：`src-tauri/src/network_library.rs`、`src-tauri/src/network_fetch_job.rs`、`src-tauri/src/network_p2.rs`、`scripts/verify-tauri.mjs`。

### UI 轻操作返回全量快照（复发型坑）：侧栏点行卡顿

- **日期**：2026-08-12
- **症状 / 背景**：本地货架点「容器」行（如 HYmd）要等约 1 秒才切换中列；网络索引越大越慢。与「网络列表点行卡顿」「工作区开眼慢」同属一类：**轻操作用了全量快照**。
- **走过的弯路**：只给网络勾选与工作区开眼做了轻快照；`set_nav` / `set_filters` / `set_cluster_mode` 等热路径仍调 `snapshot_now()`，每次点击重建并序列化全部网络列表 **DTO**（Data Transfer Object，跨进程传给前端的结构化数据，此处约 8000+ 条、数 MB JSON）。
- **最终正确做法**（读码 + `verify:tauri` 192 测 + 热路径静态检查 **已验证**；人手点容器行手感 **待验证**）：
  1. 热路径命令一律返 `snapshot_now_light`（省略网络列表；nav/项目/工作区/永久库/detail 仍完整）：`set_nav`、`set_workspace_visibility`、`set_default_workspace`、`set_filters`、`set_cluster_mode`、`set_purpose_domain_filter`、`set_ui_layout`、`reorder_workspace`。
  2. 前端已有 `mergeNavOnlySnapshot` / `mergeOmitNetworkSnapshot`：识别省略哨兵 `__omit_network_list__`，从旧状态回填网络列表，无需改 UI。
  3. **默认轻、例外全量**：新增「返回快照」的后端命令时默认 `snapshot_now_light`；仅当网络列表内容/顺序确实变化（拉取、热度、网络排序、首次全量加载等）才允许 `snapshot_now()`。
  4. 防回归：`scripts/verify-tauri.mjs` 静态提取上述热路径函数体，断言含 `snapshot_now_light` 且不含 `snapshot_now()`。
- **关键文件**：`src-tauri/src/lib.rs`、`src/App.tsx`（`mergeNavOnlySnapshot`）、`scripts/verify-tauri.mjs`。

### 网络列表点行卡顿：选择操作误用全量快照 + 调试插桩残留

- **日期**：2026-08-12
- **症状 / 背景**：网络工作台（中间列表，8000+ 条）点一行勾选就要等约 1 秒起；点哪都会重建右侧详情，资源浪费。
- **走过的弯路**：
  1. 行点击直连 `set_selection` → `snapshot_now()` 全量快照：重载 settings/台账 + **重建并序列化全部网络列表 DTO**（数 MB JSON）+ 读选中条目 markdown，勾一个框也全跑一遍。
  2. 排障期的 `#region agent log` 插桩（同步写 `debug-10020b.log` 的调试日志块）留在快照构建、网络列表构建与 App 渲染热路径里，每次交互再加文件写与额外 IPC。
- **最终正确做法**（读码 + 191 项库测 + typecheck/verify **已验证**；人手点击手感 **待验证**）：
