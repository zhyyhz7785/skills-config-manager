# 工作面隔离原则

> **硬约束**：改 CursorConfigManager **软件代码**，与改永久库里的 **skills / rules 正文**，必须绝对隔离。两条工作面互不嵌套、互不渗入。

## 结论

本软件只管理「资产在哪里、往哪放」；永久库里的 skills / rules 只承载「AI 该怎么做事」。  
因此：

| 工作面 | 可以想什么 | 禁止想什么 |
|--------|------------|------------|
| **A. 写 skills / rules** | 领域约束、触发条件、说明文字、对 AI 的行为要求 | 管理器实现、IPC、服务类、catalog schema、扫描算法细节 |
| **B. 写管理器代码** | 路径、目录约定、`libraryPath`、容器根、Move/Deploy/Withdraw、台账字段 | skills / rules **正文语义**（条文、流程、领域判断） |

一句话：**编内容时当管理器不存在；写代码时当正文是不透明字节，只认路径。**

## 关键前提

1. **永久库**（当前常为 `E:\cursor\CursorSkills` 或设置中的 `LibraryRoot`）是 skills / rules 的**内容权威源**。
2. **CursorConfigManager** 是路径与台账的**操作器**：登记、迁入、部署、移出、对账；不是内容编辑器，也不是领域专家系统。
3. Cursor / Claude / Codex 运行时只读**容器内路径**上的文件；管理器代码不参与解释正文。

## 作用机制

```text
工作面 A（内容）          工作面 B（软件）
┌─────────────────┐      ┌──────────────────────┐
│ skills/**       │      │ electron/ / src/      │
│ rules/**        │ ──路径与台账──▶ │ catalog.json 读写   │
│ 正文 = AI 指令  │      │ Move / Deploy 只动路径│
└─────────────────┘      └──────────────────────┘
         ▲                          ▲
         │                          │
   只改语义与结构              只改路径契约与 UI
   不读 CCM 源码               不解析正文含义
```

- 管理器对库内文件的合法依赖只有：**相对路径、是否存在、哈希（完整性）、frontmatter 里已约定的元数据键**（如 `description`、`alwaysApply`）。
- 管理器**不得**把某条 rule 的领域条款（例如「安全系数如何判」）写进 TypeScript 分支；也**不得**要求写 skill 时迁就某个服务函数名。
- 写 skill / rule 时**不得**出现「为了兼容某某 Service / 某次 reconcile」而改写领域正文；路径与命名遵循库约定即可，实现细节留给软件侧。

## 边界与取舍

**允许的薄耦合（仅路径与契约）**

- 目录布局：`skills/<id>/`、`rules/<id>/<id>.mdc`
- 台账字段：`id`、`kind`、`libraryPath`、`contentHash`、`deployedPath` 等
- frontmatter 中软件已约定读取的键；新增键须先改软件契约，再在内容侧使用

**禁止的耦合**

- 在管理器代码里 `includes("安全系数")`、按正文关键词做业务分支
- 在 skill / rule 正文里描述「打开 CursorConfigManager 点某某按钮才能生效」作为领域步骤（生效由 Deploy 路径完成，不是内容逻辑）
- 同一会话、同一提交里混改「大段领域正文」与「管理器算法」且不拆开审阅——易把内容语义泄漏进代码，或把实现细节泄漏进规则

**并发操作**

- 手改 `catalog.json` 或大面积重排库文件时：**不要同时运行**管理器（它会把 catalog 读入内存再整体回写，可能覆盖手改）。
- 改 skills / rules 正文时可以不启管理器；需要 Deploy / 对账时再开软件。

## 对日常工作的直接要求

1. **任务开场先定性工作面**：本次是 A（内容）还是 B（软件）？默认只动一面。
2. **A 面交付物**：`.md` / `.mdc` / skill 目录；验收看 AI 行为与文档结构，不看 TypeScript 是否编译。
3. **B 面交付物**：TS/React/IPC/测试；验收看路径移动、台账一致、UI 命令，不抽查 rule 条文是否「写得对」。
4. **跨面需求必须拆单**：例如「新增 D10 规则并让管理器识别聚类 ID」→ 先 A 落正文与路径，再 B 做扫描/字段；或先 B 扩契约，再 A 使用新键。禁止在一个含糊任务里两边同时「顺便改」。
