# 自动归类结果 vs 原划分原则：对比与审视

> 目的：对照你原先的 L0 / L1(D·T·G) / L2 原则，说明软件**现行**自动归类实际在做什么，标出错位点，供审视后优化。  
> 原原则（内容侧）：[`CursorSkills/005-CursorSkills-Rules盘点与分类优化-2026-07-22.md`](../../../../CursorSkills/005-CursorSkills-Rules盘点与分类优化-2026-07-22.md)。  
> 现行实现（软件侧）：[`007`](007-无catalog时L0L1L2划分逻辑-2026-07-26.md)、`purposeTaxonomyHelper.suggestLevel` / `deriveLevel`。  
> 结论可信度：**已验证**（对照 005 正文与当时代码）。  
> **后续（同日已实施）**：按审视结论采用映射 **1A / 树 2A**——仅项目→L2、用户级 Cursor 规则→L0，其余「未分类」+ 拖拽定级；详见 [007](007-无catalog时L0L1L2划分逻辑-2026-07-26.md)。下文 §3 起保留当时错位分析，供对照。

## 1. 一句话差距

| 面 | L0 / L1 / L2 回答的问题 |
|----|-------------------------|
| **你的原则（005）** | 这条约束对**多少项目成立**？因**什么任务**触发？L1 再按 D/T/G **正交聚类** |
| **现行软件** | 这条资产来自**哪类路径/scope**？规则 frontmatter 是否 **alwaysApply**？用途关键词猜 **purposes** |

结果上：自动归类容易把大量技能/规则一律标成 **「L1 通用包」**，把「永久库存货」和「真正的 L1 聚类包」混在同一层；**几乎不会**按你的准入条件认出真正的 L0（定稿用户规则）或 L1 的 D10/T00/T10 包身份。

## 2. 原原则摘要（005，你要的语义）

组合关系（不是目录树继承）：

```text
L0 顶级用户规则（固定一份、长期、跨项目）
  + L1 零个或多个聚类包（D 领域 / T 技术栈 / G 治理，多选）
  + L2 项目增量（只写本仓差异）
  = 当前项目有效规则集
```

| 层级 | 应回答 | 准入要点（005） | 二级结构 |
|------|--------|-----------------|----------|
| **L0** | 「我希望 AI **始终**怎样工作？」 | 几乎所有项目成立；长期稳定；与项目名/技术栈/领域无关；不绑具体 Skill/路径 | 原则上**一份**定稿（如 `01-cursor-user-rules-…`） |
| **L1** | 「做**这一类**工作时还必须遵守什么？」 | ≥2 无关项目需要 + 有真实正文 + 触发可写清；未达标只留编号 | **D / T / G** 三维；活跃例：D10、T00、T10 |
| **L2** | 「**这个仓库**具体怎样工作？例外是什么？」 | 只写增量；禁止复述 L0/L1 | 按**项目** |

005 明确：**软件不得靠正文语义做学科判定**；可读 frontmatter 触发字段与路径/台账。聚类身份（D10 vs T10）在规划里靠**命名与清单**，不是靠管理器读懂正文。

## 3. 现行软件逻辑（2026-07-26，已验证）

### 3.1 自动归类建议层级 `suggestLevel`

```text
已有 tags.level？ → 保持
否则 项目 scope / origins？ → L2「来自项目容器」
否则 规则 alwaysApply=true？ → L0
否则（含全部 skill/agent/command/hook、其余规则）→ L1
```

### 3.2 列表展示 `deriveLevel`（确认写入前/后）

```text
tags.level？ → 用之
否则 项目 scope？ → L2
否则 → L1
```

注意：列表**不读** `alwaysApply`；未写入 `tags.level` 时，即使用户规则是 alwaysApply，界面上也先落在 L1，直到归类确认。

### 3.3 二级分组（与 005 的 D/T/G 不同）

| 层级 | 现行二级组 |
|------|------------|
| L0 | 固定「顶级规则」 |
| L1 | `tags.purposes` 用途域（如「工程项目 / 建筑」「代码 / Cursor」）或「未分类」 |
| L2 | 「项目规则 / {登记项目名}」 |

用途 `purposes` 来自关键词启发式（`suggestPurpose`），维度接近旧「工程/代码/学习/元工具」，**不是** 005 的 D/T/G。

### 3.4 来源展示（与层级正交）

来源只说明存放处：**用户文档** / **项目文档 · 名** / **永久库**；不单独决定 L1 子类（仅项目来源强推 L2）。

## 4. 对照表：同名层级，不同判据

| 维度 | 原原则（005） | 现行自动归类 | 错位程度 |
|------|---------------|--------------|----------|
| **L0 是什么** | 跨项目个人底线规则，**内容准入**极严，通常一份 | 任意规则 `alwaysApply: true` | **高**：005 里 G90 原料也曾 alwaysApply，却**不是** L0 |
| **L1 是什么** | 可复用**聚类包**（D/T/G），有实例化门槛 | 「非项目来源」的默认桶；技能也整批进 L1 | **高**：库存技能 ≠ 聚类规则包 |
| **L1 二级** | D10 / T00 / T10 / G90… | purposes（工程·建筑、元工具·文档…） | **高**：两套正交模型未对齐 |
| **L2 是什么** | 单项目增量正文 | `scope` 以 `project:` 开头（或 origins） | **中**：方向一致，但「曾在项目扫到、现已入库且 scope 未校准」会漏判/误判 |
| **技能 / 代理等** | 005 主要谈 **rules** 分层；skill 另属能力资产 | 与规则同一套 L0/L1/L2 | **中**：把 skill 标 L1「通用包」语义含糊 |
| **文件名 L1T…** | 内容侧命名约定，便于人眼与清单 | **刻意不读**（避免普通用户依赖命名） | **有意取舍**：保护通用用户，牺牲对你库的「已命名即身份」 |
| **永久库路径** | 权威源位置，不决定层级 | 来源标「永久库」，层级仍多落 L1 | **中**：位置与层级解耦正确，但缺「是否聚类包」信号 |

## 5. 为何你会觉得「结果不满意」（机制解释）

以下为**推断**（由上表推出；未对你当前 55 条建议逐条审计）：

1. **L1 过宽**  
   凡非项目 scope 且非 alwaysApply 的规则，以及几乎全部技能，都建议 L1。截图里大量 `永久库 · CursorSkills/skills/…` +「L1 通用包」符合现行代码，但不符合 005「L1 = 达标聚类包」。

2. **L0 过窄或过偏**  
   - 过偏：任何 `alwaysApply: true` 都进 L0 → 与 005「L0 仅跨项目底线」冲突（治理原料、项目内 alwaysApply 会误入）。  
   - 过窄于你的定稿：若 `01-cursor-user-rules` **未**标 alwaysApply，或未以 rule 形态被读到 frontmatter，则**进不了** L0，只会进 L1。

3. **D/T/G 消失**  
   二级组改走 purposes 后，界面不再出现「规则包 / 技术栈」「规则包 / 领域」。你原来靠命名看见的结构，软件不再复现。

4. **用途启发式噪声**  
   `suggestPurpose` 用 id/备注/描述关键词匹配（如 hit「建筑」→ `engineering.building`）。这是用途标签，不是层级；叠在「一律 L1」上会显得「乱贴学科」。

5. **工作面约束的硬边界**  
   005 §2.4 禁止软件读正文做学科分类。因此软件**不能**自动执行「是否几乎所有项目成立」这类 L0 准入——除非增加**白名单 / 台账字段 / 清单**等非正文信号。现行用 alwaysApply 是「唯一客观 frontmatter」，但与 005 语义不等价。

## 6. 信号能力边界（优化时先认清）

| 信号 | 软件可否用 | 对 005 的帮助 |
|------|------------|----------------|
| `tags.scope` / origins 项目 | 可以 | L2 主信号（已用） |
| frontmatter `alwaysApply` / `globs` | 可以（结构化） | 触发方式；**不足以**单独定义 L0/L1 |
| 来源用户级 vs 永久库 | 可以 | 展示「在哪」；不定义聚类身份 |
| 文件名 `L1T10-…` / `L2P-…` | 可以但你已要求**不作默认依据** | 对你私人库很准，对普通用户不友好 |
| catalog 显式 `tags.level` / 未来 `clusterId` | 可以 | 与 005 对齐的正途 |
| 正文「是否跨项目成立」 | **禁止**（005 隔离） | 只能人判或外部清单 |

## 7. 优化方向候选（供你拍板，非实施）

按与 005 贴合程度排序；选 1～2 条再改代码即可。

### A. 分层对象分流（推荐优先讨论）

- **规则**：继续谈 L0/L1/L2。  
- **技能 / 代理 / 命令 / 钩子**：自动归类**只建议用途**，层级默认「不适用」或固定不进 L0/L2 树（或单独「能力资产」区）。  
避免「35 个技能全是 L1 通用包」。

### B. L0 白名单 / 台账字段

- 增加 `tags.role = top-user-rule | cluster | project-delta`（或沿用 level + `clusterKey`）。  
- L0 **仅**白名单 id / 用户钉选；`alwaysApply` 只作为「触发提示」，不直接升 L0。  
对齐 005「L0 一份定稿」。

### C. L1 与 D/T/G 对齐（需内容侧契约）

在**不读正文**前提下二选一或组合：

1. **可选**识别已知前缀（仅当设置「启用库内命名约定」打开时读 `L1D`/`L1T`/`L1G`）；或  
2. 台账字段 `tags.cluster = D10|T00|…`，由你在归类弹窗里改选，软件只存不猜。  

purposes 保留为「用途」，与 cluster **并列**，不再冒充 L1 二级主轴。

### D. L2 校准

- 建库后强制 `rematchProjectScopes` 结果参与建议（已有 rematch，需确认建议用的是校准后 scope）。  
- 「永久库但 origins 曾是项目」→ 建议 L2 或标「曾属项目，请确认」。

### E. 归类 UX（降低一次全选的伤害）

- 默认**不**全选 L1 技能；或按类型默认：规则勾选、技能不勾选。  
- 弹窗支持改层级下拉（L0/L1/L2），而不仅是勾选写入建议值。  
- 对 `tentative` 项默认不勾选。

### F. 明确「不满意」的验收句（建议你勾选）

写优化前先定验收，例如：

- [ ] L0 区最多出现我钉选的那份用户规则（或白名单）。  
- [ ] L1 区二级为 D/T/G（或 cluster 名），不是 purposes。  
- [ ] 技能不出现在 L0/L1/L2 层级建议里，或单独列表。  
- [ ] 项目扫入的规则默认 L2，且带来源项目名。  
- [ ] 全选写入后，永久库树与 005 活跃聚类表可对上。

## 8. 建议的审视顺序

1. 打开一次自动归类预览，抽 5 条你认为「明显错」的：记下**现行建议层级** vs **你期望层级**。  
2. 对照 §4 表，判断错因属于：L0←alwaysApply、L1 过宽、缺 D/T/G、技能不该分层、scope 未校准。  
3. 在 §7 的 A–E 中勾选要做的项，再开实施（可另写 Plan）。
