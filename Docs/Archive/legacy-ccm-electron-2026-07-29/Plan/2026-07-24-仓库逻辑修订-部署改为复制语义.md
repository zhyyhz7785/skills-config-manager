# 仓库逻辑修订：部署改为复制语义（备份库常驻正本）

关联计划：[2026-07-24-仓库逻辑修订-同文档多目录版本比对.md](./2026-07-24-仓库逻辑修订-同文档多目录版本比对.md)（该计划只做冲突弹窗信息增强，本计划做核心语义修订；两者可合并实施，弹窗增强部分不在本文重复展开）。

## 结论

把"放入容器"从 Move（移动，文件从源位置消失）改为 Copy（复制，源位置保留），使备份库始终保留一份正本。"存入备份库"时按 SHA-256（一种内容哈希算法，内容相同则哈希值相同）比对容器副本与库内正本：

- 内容相同：静默删除容器副本，不打扰用户。
- 内容不同：弹出冲突比对窗，展示两侧文件信息（路径、哈希、大小、修改时间、内容预览），由用户选择保留哪个版本。

## 问题根源（已验证）

当前 `deployToContainer()`（`electron/services/skillIngestService.ts` 约 924–969 行）执行的是物理移动：库文件被搬到容器后，`isInLibrary=false`，备份库目录里不再有该文档。因此"文档在使用中 ⇒ 备份库为空"，不符合用户对"备份库"的预期。

而"内容相同自动删容器副本"已经存在：`moveIntoBackupLibrary()` 约 663–692 行，`sameContent / sameAsLibrary` 分支会删容器副本并保留库内文件。缺的是"库内常驻正本"这一前提。

## 目标状态模型

台账（catalog.json，记录每个条目状态的账本文件）中 `isInLibrary` 与 `deployedPath` 不再互斥，新增"双份态"：

| 状态 | isInLibrary | deployedPath | 磁盘 |
|---|---|---|---|
| 仅在库 | true | 空 | 只有库内正本 |
| 双份（新常态） | true | 容器路径 | 库正本 + 容器副本 |
| 仅容器（遗留/扫描登记） | false | 容器路径 | 只有容器文件 |

列表分区（"容器中 / 曾用 / 备份库余量"）已按 live-path（活动容器中实际存活的文件路径）互斥判定（`libraryCatalogService.ts` 714–757 行），双份态可直接兼容，无需改分区逻辑。`inferOne`（1216–1228 行）与 `relinkDeployedPathsFromDiscovered` 也已支持双份，保留不动。

## 改动清单

### 1. 部署改为复制 — `electron/services/skillIngestService.ts`

`deployToContainer()`（924–969 行）：

- Move 改 Copy：`moveDirectoryCrossVolume`/`moveFileCrossVolume` 换为纯复制（在 `fsMove.ts` 新增 `copyFileToDir`/`copyDirectory`，复用其中已有的递归拷贝代码，不删源）。
- 台账更新改为：保持 `isInLibrary=true`、保留 `libraryPath`，设 `deployedPath=target`。
- 门禁改为：要求库文件存在（`libraryPath` 有效），且目标容器无同名/无存活副本；去掉 `!isInLibrary` 即抛错的旧门禁（924–927 行）。
- 历史记录 `kind` 沿用 `deployed`，note 改为「复制到容器」。

### 2. 存回备份库 = 比对后删副本或走冲突 — 同文件

`withdrawToLibrary()`（971–1025 行）：双份态下现在会因 `destDir` 已存在而盲目另存 `-w` 新 id（985–1004 行），必须改为：

- 库正本存在且哈希与容器副本相同 → 删容器副本，`deployedPath=''`，完成。
- 哈希不同 → 返回冲突项（复用 `PathConflictItem`），交用户决议后再执行；决议选项：保留库版本（删容器副本）/ 用容器版本覆盖库 / 另存新 id / 跳过。
- 库正本不存在（遗留纯容器条目）→ 维持现有 Move 入库行为。

`moveIntoBackupLibrary()`（603–784 行）：同内容删副本与冲突收集逻辑基本可复用，只需确认双份态下 `comparePath` 优先取 `libraryPath`（635–642 行已如此），并统一冲突决议选项语义与上面一致。

### 3. 命令可用性 — `electron/appController.ts`

`buildCommands`（819–828 行）：`canDeploy = all isInLibrary`、`canWithdraw = all !isInLibrary` 的互斥假设失效，改为：

- `canDeploy`：库文件存在，且当前容器无该条目存活副本。
- `canWithdraw`：存在存活的容器副本（`deployedPath`/live-path 有效），不再看 `isInLibrary`。

### 4. 恢复初始的选源修正 — `skillIngestService.ts`

`resolveCurrentManagedPath()`（1689–1704 行）在 `isInLibrary=true` 时只返回库路径。双份态下"恢复初始"会把库正本搬走，破坏"库常驻"目标。改为：

- 恢复初始操作优先取容器副本作为搬运源；库正本不动。
- 无容器副本时，从库复制（不移动）到 initial 位置。
- `restoreAllToInitialWithResolutions()`（822–921 行）恢复后台账不再强制 `isInLibrary=false`，按磁盘实际情况写。

### 5. 状态文案与详情 — `shared/types.ts`、`appController.ts`

- `libraryEntryLocationDisplay`（`shared/types.ts` 378–380 行）：二选一文案增加"在库＋容器"双份态。
- 详情"当前路径"（`appController.ts` 785 行）：双份态同时展示库路径与容器路径。

### 6. 扫描标注 — `electron/services/skillScanService.ts`

`annotateAgainstCatalog`（166–197 行）：双份且哈希一致的容器文件不再标 `needsAttention`（避免把正常部署副本当待处理项）。

### 7. 冲突弹窗文件信息 — `src/App.tsx`、`shared/types.ts`

按关联计划执行：`PathConflictItem` 增加大小、修改时间等可选字段，`ConflictCompareModal`（`App.tsx` 约 1600–1691 行）增加元数据对比表。本计划新增一点：迁入方向的选项 UI 需补上「保留库版本」（后端 `merge` 已支持，UI 未暴露）。

## 旧数据兼容

- 已部署但库内无文件的旧条目（旧 Move 部署产物）：不做一次性迁移；用户下次"存入备份库"时走第 2 条的"库正本不存在"分支自然补齐。
- 台账无新增必填字段，`catalog.json` 无需迁移脚本。

## 实施顺序

1. `fsMove.ts` 增加复制原语；`deployToContainer` 改 Copy（改动 1）。
2. `withdrawToLibrary` / `moveIntoBackupLibrary` 比对与冲突（改动 2）。
3. `buildCommands` 与恢复初始选源（改动 3、4）。
4. 文案、扫描标注、冲突弹窗增强（改动 5、6、7）。
5. 测试验证。

## 测试验证（待验证）

1. 部署后检查：库目录仍有正本，容器有副本，条目仍显示在"容器中"分区。
2. 不改动容器副本，执行"存入备份库"：容器副本被静默删除，无弹窗，条目回到"曾用"分区。
3. 修改容器副本后执行"存入备份库"：弹出冲突窗，元数据（哈希、大小、修改时间、预览）正确，四个选项各自行为正确。
4. 恢复初始：库正本不被搬走；容器副本回到 initial 位置。
5. 旧数据：构造一个"仅容器"遗留条目，存入备份库走 Move 入库，行为与现在一致。
6. 跨卷部署（库与容器在不同盘符）复制正常。

## 边界与暂不处理

- 台账 `deployedPath` 仍是单值，同一条目同时部署到多个容器暂不支持（多容器识别靠扫描 relink，行为与现状一致）。
- `orphans` 与嵌套路径修复逻辑（1230–1293 行）不在本次范围。
