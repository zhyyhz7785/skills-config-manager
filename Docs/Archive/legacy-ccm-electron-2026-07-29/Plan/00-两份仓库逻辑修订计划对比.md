## 为何 B 更好（前提 → 机制）

**前提（用户期望）**：备份库应始终能看到文档；同一份在多处时，存回要按是否改过自动处理或让人选。

**机制**：

1. 今日部署是 Move → 使用中库必空 → 「多目录双份」很少成立。
2. A 增强的元数据（大小、修改时间、预览行数）只有在冲突弹窗真正频繁出现时才有价值；根因不改，弹窗很少被用到。
3. B 把双份变成常态后，现有 SHA-256（内容哈希，相同内容得到相同摘要）同删分支才稳定触发；异内容再走冲突窗——此时再做 A 的信息增强才划算。

## A 仍有价值的部分

下列内容应保留并并入 B 实施，不要丢弃 A：

- `PathConflictItem` 增加 `sourceSize` / `targetSize` / `sourceModified` / `targetModified` 等可选字段
- `buildConflict` / `readPreview` 收集元数据与前若干行预览
- `ConflictCompareModal` 元数据对比表与样式
- 测试场景中「冲突窗展示是否够用」的检查项

B 已写「按关联计划执行」并额外要求 UI 暴露「保留库版本」（后端 `merge` 已有）；以 B 为主线时，把 A 当作改动 7 的细案即可。

## 建议执行策略

1. **主线只跟 B**：实施顺序仍按 B（复制原语 → 存回比对 → 命令/恢复 → 文案与弹窗）。
2. **实施到改动 7 时展开 A**：类型与弹窗按 A 的字段与 UI 草案落地，避免两份计划各改一遍。
3. **A 文件处置（建议）**：保留作弹窗增强细案，或在文首加一句「已并入 B，勿单独当主线」；不必删，避免丢细节。
4. **不要只做 A**：做完 A 用户原问题仍在。
