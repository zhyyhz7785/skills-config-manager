# 项目文档固定结构管理

> **原则**：固定文档名称，只原地更新；分类明确；子目录固定 5 个；避免文档爆炸导致后期查询困难。

---

## 文档根路径

| 模式 | 路径 | 适用 |
|---|---|---|
| **仓库级**（默认） | `Docs/` 或 `docs/` | 单主题项目 |
| **主题级** | `docs/{主题}/` 或 `Docs/{主题}/` | 大仓多主题 |

**大小写**：以仓库既有约定为准（`Docs/` 与 `docs/` 均可，不强制统一）。

**选定规则**：
- 用户 `@` 了具体主题目录 → 在该主题目录套用本结构
- 用户说「初始化文档」且仓库已有 `docs/` 多主题 → 问清主题名，在 `docs/{主题}/` 创建
- 单主题小项目 → 仓库根 `Docs/` 或 `docs/` 一套即可

下文用 `{DOCS}` 代指上述任一根路径（如 `Docs/`、`docs/{主题}/`）。

---

## 使用方式

当用户触发以下场景时，**必须**按本 skill 执行：

| 触发词 / 场景 | 动作 |
|---|---|
| 「初始化文档」「建立文档结构」「搭建 Docs」 | 只建 `{DOCS}` 5 子目录 + 6 核心文件；每文件正文一句「已初始化。」；不套模板、不提炼 |
| 「更新日志」「同步状态」「更新文档」 | **仅本轮用户点名才写**；更新 `03-实施与状态`；核心逻辑/架构/启动流程变化时连带更新 01/02/04；本次有「多轮才通过」的经验则追加写入 05；**不**改 06 |
| 「记经验」「踩坑记录」「整理实现细节」「记到 05」 | **只**更新 `05-经验教训.md`（先过判定门槛，按主题追加条目，不新建平行文件） |
| 「完善启动文档」「发行路径」「打包用时」「步骤用时」等 | **只**更新 `04-启动与测试.md`：三节（日常测试 / 网页测试 / 完整打包）必须齐全；命令放代码块、成品路径、用时估计 |
| 「压缩文档」「精简文档」「文档瘦身」「清理文档」 | 按协议 6：删除 Learning/Research/Plan/Evaluations 中已脱离 01～05 的文件；核心文档、活跃 00 与子目录骨架不动 |
| 为了**懂** | 写入 `{DOCS}/Learning/`，**不**在根目录新建文档 |
| 为了**选** | 写入 `{DOCS}/Research/`，**不**在根目录新建文档 |
| 「总体计划」「00 计划」「全局视野」「高度抽象」「多年路线」「顶层锚定」；点名旧名 `L0-personal-abstract-plan-doc` | 写/改 `{DOCS}/Plan/00-<主题>-<副标题>.md`（见「Plan/ 两层」） |
| 阶段设计、执行计划、MVP 蓝本、具体执行、详细排期 | 写入 `{DOCS}/Plan/{序号}-…-{yyyyMMdd}.md`，**不**堆在根目录、**不**写入 00 |
| 金标准评估、阶段结案记录 | 写入 `{DOCS}/Evaluations/` |
| 「用核心逻辑写」「像核心逻辑那样」「L0 文档思维」「生成核心逻辑文档」「01 风格写 Research/Plan」 | 按下方 01 模板写或改 `{DOCS}/01-核心逻辑.md`；若明确写 Research/Plan，落对应子目录，章节仍用 01 的 1～6 |

## 目录结构（固定）

```
{DOCS}/
├── README.md              # 文档导航 + 使用方法
├── 01-核心逻辑.md          # 人类阅读：为难谁、给谁用、什么机制、边界在哪（活文档）
├── 02-项目架构.md          # AI 阅读：模块职责、目录映射、数据流、关键决策（活文档）
├── 03-实施与状态.md        # 阶段、版本快照、最近变更、下一步、已知问题（活文档）
├── 04-启动与测试.md        # 日常测试 / 网页测试 / 完整打包；命令全在代码块
├── 05-经验教训.md          # 只记多轮修改才通过的工程经验（活文档）
├── 06-帮助文档.md          # 【可选】最终用户手册；仅显式「生成帮助」时写；本 skill 不碰
├── Research/              # 为了选：用户逻辑（自上而下）
├── Learning/              # 为了懂：第一性原理（自下而上）
├── Archive/               # 过期文档归档
├── Plan/                  # 00 总体计划（自己看的框架）+ 编号执行计划
└── Evaluations/           # 金标准评估与结案记录
```

### 人类阅读 vs AI 阅读（01 与 02 的分工，必读）

同一个项目要同时服务两类读者，写法不同，不能混在一篇里：

| | 01-核心逻辑（给人读） | 02-项目架构（给 AI 读） |
|---|---|---|
| 回答什么 | 这软件在干什么、为难谁、凭什么这么设计 | 模块在哪、数据怎么流、改功能该动哪个文件 |
| 写法 | 结论先行、对比表、允许类比与口诀帮记忆 | 结构化表格、路径精确到文件、命名与代码一致 |
| 禁止 | 堆源码路径、接口签名、行级细节 | 类比、比喻、模糊指代（如「那个模块」「相关文件」） |

**判别法**：一段内容删掉后「新用户看不懂产品」→ 归 01；删掉后「AI 改码找不到位置」→ 归 02。

### 两个思考方向（Learning vs Research 只在此处定义）

| 方向 | 是什么 | 起什么作用 | 产物落点 |
|---|---|---|---|
| **第一性原理**（自下而上） | 从不可再拆的起点往上重建 | 为了**懂**：拆开黑箱、学原理、建知识架构 | `Learning/` |
| **用户逻辑**（自上而下，别名顶层逻辑） | 从用户/客户场景倒推最佳实现，技术当黑箱 | 为了**选**：对比方案与竞品，不进实现细节 | `Research/`；`01-核心逻辑.md` 正文也按此方向写 |

写完这篇是为了**懂**还是为了**选**？懂 → Learning；选 → Research。还分不清 → 有方案/竞品对比表的进 Research，其余进 Learning。

### 各文档分工（写什么 / 不写什么 / 更新时机）

| 写哪里 | 写什么 | 不写什么 | 更新时机 |
|---|---|---|---|
| **01-核心逻辑** | 问题陈述、目标用户、机制模型（不展开实现）、硬边界与口诀 | 源码路径、实现细节、启动命令、试错过程 | 产品定位 / 机制 / 边界变化时 |
| **02-项目架构** | 模块职责、目录映射、数据流、关键决策一句话理由 | 行级细节、试错过程、用户故事 | 模块 / 路径 / 数据流 / 选型变化时 |
| **03-实施与状态** | 阶段划分、版本快照、最近变更、待办优先级、已知问题与风险 | 已定稿工程经验（归 05）、启动命令（归 04） | 用户点名「更新日志」时 |
| **04-启动与测试** | 日常测试、网页测试、完整打包三节齐全；命令全放代码块；长步骤写用时与成品绝对路径 | 经验教训（归 05）、产品逻辑（归 01） | 启动 / 测试 / 打包命令有变化时 |
| **05-经验教训** | **多轮修改才通过**的问题：弯路清单 + 最终正确做法 + 禁令 | 一次通过的常规实现、待办、状态百分比、概念科普 | 多轮才通过的问题定稿后追加 |
| **06-帮助文档**（可选） | 最终用户怎么用；推荐流程 + 等价操作表 | 编译命令、源码路径、实现细节 | 仅用户显式说「生成帮助 / 更新帮助」时；**本 skill 一律不碰 06** |
| **Plan/** | 00：自己看的全局框架（≤200 行）；01/…：下一阶段怎么做 | 已落地的「当前正确做法」（定稿后提炼进 05）；状态快照（归 03）；00 里禁止代码/接口/选型表 | 00 点名总体计划时原地更新；编号文件阶段启动 / 定稿时 |
| **Learning/** | 为了懂：原理、基础、知识架构（第一性/自下而上） | 竞品对比、选型决策（那是选 → Research） | 学习笔记追加 |
| **Research/** | 为了选：用户场景、竞品、实现手段（用户逻辑/自上而下） | 拆黑箱学原理（那是懂 → Learning）；状态快照（归 03） | 调研完成时追加 |
| **Evaluations/** | 金标准评估、阶段结案 | 不替代 03 的当前状态 | 阶段结案时写一次 |
| **Archive/** | 核心文档与 00 大改版前的旧版本 | 活跃正文 | 大改版前 |

**禁止**：把状态快照写进 Plan/ 或 Research/ 替代 03；Plan/ 编号文件带日期可以，00 与 03/05 不允许带日期平行版本。

**05 写入时机与判定门槛**：该问题是否经历「首次尝试失败 → 多轮修改 → 最终通过」？是（无论人为失误还是 AI 失误）→ 记；否（一次就做对）→ **不记**，记了只会稀释检索价值。

**05 条目粒度**：一个难啃问题 = 一条；同主题再次踩坑 → **原地增补**该条，不新建平行标题堆叠。

## 子目录规范

### 命名规范

子目录新建文件：`{序号}-{文件名}-{yyyyMMdd}.md`，序号 = 该目录现有最大序号 + 1。核心 6 文件是固定名，不加序号日期。与本文写作纪律第 14 条同一套。

| 目录 | 用途 | 文件命名 |
|---|---|---|
| `Research/` | 为了选（用户逻辑） | `{序号}-{文件名}-{yyyyMMdd}.md` |
| `Learning/` | 为了懂（第一性原理） | `{序号}-{文件名}-{yyyyMMdd}.md` |
| `Archive/` | 核心文档与 00 大改版前的旧版本 | `{序号}-{原文件名}-归档-{yyyyMMdd}.md` |
| `Plan/` | 00 总体计划 + 编号执行计划（见「Plan/ 两层」） | `{序号}-{文件名}-{yyyyMMdd}.md`；例外：00 用固定名单一活跃文件、原地更新、无日期 |
| `Evaluations/` | 阶段/版本结案评估 | `{序号}-{文件名}-{yyyyMMdd}.md` |

### 扩展规则

- 固定 **5 个子目录**：`Research/` / `Learning/` / `Archive/` / `Plan/` / `Evaluations/`（初始化一律建齐）
- 总数 **恰好 5 个**；禁止另开第 6 个子目录
- 根目录文件：固定 6 个核心文档（README + 01~05）；**可选**第 7 个 `06-帮助文档.md`（仅显式「生成帮助」时才有；初始化时不创建）；禁止第 8 个及以上文件

## Plan/ 两层

`00` 是给自己看的全局视野（高度抽象）；`01/02/…` 是给人+AI 协作执行的具体计划。点名旧 skill 名 `L0-personal-abstract-plan-doc` 时仍按本节执行。节结构按项目自适应；需要齐套骨架时用下方「00 可选 12 节模板」。若 `{DOCS}/Plan/` 不存在，先按协议 1 补建 5 子目录再写。

| | 00 总体计划 | 01/02/… 执行计划 |
|---|---|---|
| 目的 | 全局视野、快速浏览 | 落地实施、协作执行 |
| 受众 | 用户自己 | 用户 + AI |
| 文件 | `{DOCS}/Plan/00-<主题>-<副标题>.md`；无日期；同一 `{DOCS}` 只有一份 | `{DOCS}/Plan/{序号}-{文件名}-{yyyyMMdd}.md` |
| 修订 | 原地更新；大改版先把旧版复制到 `{DOCS}/Archive/`，不留两个活跃 00 | 每阶段可新建 |
| 篇幅 | ≤ 200 行（硬约束） | 不限 |
| 内容 | 只写框架；禁止程序代码 / 接口 / 选型表 / 案例清单 | 允许细节 |
| 细节 | 一句话链到 `Plan/01-…` 或同 `{DOCS}` 下 Research/Learning | 本文展开 |

**三条铁律**（只约束 00）：全文 ≤ 200 行；禁止细节；细节下沉。超过 200 行即重写，不许扩。

**反向**：用户说「具体执行 / 技术方案 / 详细排期 / 写接口 / 列模块清单」→ 写编号执行计划，不写入 00。

### 00 可选 12 节模板

**结论（建议）**：默认按项目自适应。用户要「固定 12 节 / 齐套骨架」或点名旧 skill 时用本表；三 / 四 / 六可缺，其余必写。全文 mermaid（文本绘图语法）≤ 3 个、表格 ≤ 8 张。

```text
0. 一句话定位         项目长期定位 + 短期目标
一. 不可变原则        2-4 条，永远不变的工程纪律
二. 目录结构顶层框架   只列稳定顶层，允许"预留位"标注
三. 核心机制精简       （可缺）如双轨/分层/插件机制 — 一图一表搞定
四. MVP 定义           （可缺）MVP（Minimum Viable Product，最小可行产品）：第一个用户可感知产物
五. 验证方法           证明正确的层次 + 不可妥协的铁律
六. 后期预留           （可缺）将来才启用的机制，只列"启用时机"
七. 实施步骤           分阶段，每阶段一行，带"核心交付 + 关键依赖"
八. 长期愿景           1/3/5/10 年只列时间与形态，不写技术
九. 依据与下沉         依据=本计划从哪些 L0 文档/约束得出；下沉=细节交给哪些 Plan/01… 子文档
十. 本文档使用约定     强制"只写框架 / ≤200 行 / 细节下沉 / 原地更新"
十一. 修订记录         版本表
```

| 节 | 内容上限 |
|---|---|
| 0 定位 | 1-2 句 |
| 一 原则 | 每条 1 段（2-4 行） |
| 二 目录 | 1 个目录树代码块 + 1 段依赖方向 |
| 三 机制 | 1 个 mermaid + 1 张 ≤5 行表 |
| 四 MVP | 1 张 5-7 行表 |
| 五 验证 | 1 张 3-5 行表 + 3 条铁律 |
| 六 预留 | 1 张 4-6 行表 |
| 七 步骤 | 1 个 mermaid + 1 张 ≤7 阶段表 |
| 八 愿景 | 1 张 4 行表 |
| 九 依据与下沉 | 1 张表（依据 / 下沉；依据默认只列 L0 文档） |
| 十 约定 | 1 张 4 行表 |
| 十一 修订 | 1 张表 |

## 触发协议详解

### 1. 初始化文档

**前置**：确认 `{DOCS}` 路径（仓库级 or 主题级），检查目标目录是否已存在。

**步骤**：
1. 创建 `{DOCS}/` 及固定 5 个子目录（Research / Learning / Archive / Plan / Evaluations）；**不**建 06
2. 创建 6 个核心文件（已有则跳过，不覆盖用户内容）
3. **每个文件正文只有一句** `已初始化。`（可保留 `# 标题` 与尾部版本行；版本行是硬约束，不算正文）
4. **不**套下方完整模板，**不**从 Plan / Research / 代码提炼
5. 若项目已有 `Doc/`（单数）或平铺旧文档，**不自动迁移**

占位格式示例（六个核心文件同结构，只换标题）：

```markdown
# 核心逻辑

已初始化。

**版本**：v0.0 | **更新**：{YYYY-MM-DD}
```

### 2. 更新日志

**硬禁令**：本轮用户未点名写、改、删某份文档时，不创建、不改写、不删除它，收尾不顺手补。仅当本轮用户明确说「更新文档」「更新日志」「同步状态」才开始写。

用户点名时，**必须更新** `03-实施与状态.md`（基于当前会话/近期改动，**并对照代码与测试实际状态**），其余按需；**不**更新 `06-帮助文档.md`。若核心文档仍是「已初始化」占位，先套下方完整模板再填真实内容：

| 文档 | 更新内容 |
|---|---|
| `03-实施与状态.md` | 本次完成的功能、修复、决策 → 「最近变更」；未完成项移入「下一步计划」；调整优先级；更新版本快照与已知问题 |
| `01-核心逻辑.md` | **仅当**产品定位/机制/边界有变化时更新 |
| `02-项目架构.md` | **仅当**模块/路径/数据流/技术栈有变化时更新 |
| `04-启动与测试.md` | **仅当**日常测试 / 网页测试 / 完整打包命令有变化时更新；三节仍须齐全；涉及长流程时同步核对用时估计 |
| `05-经验教训.md` | **仅当**本次有「多轮才通过」的问题定稿时追加条目 |

**禁止**：
- 新建带日期的平行文档（如 `03-实施与状态-2026-07-08.md`）
- 把状态更新写进 Research/ 或 Learning/
- 每次更新都改 01/02/04/05（无变化则不动）
- 把完整聊天记录贴进 05（只提炼弯路对照与最终方案）

**版本行**：每次更新后，修改对应文档尾部的 `**版本** | **更新**` 行。

### 3. 记录经验教训（05 专用）

用户说「记经验」「踩坑记录」「整理实现细节」「记到 05」等时：
