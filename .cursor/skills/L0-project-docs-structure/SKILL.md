# 项目文档固定结构管理

> **原则**：固定文档名称，只原地更新；分类明确；子目录固定 5 个；避免文档爆炸导致后期查询困难。

---

## 文档根路径

| 模式 | 路径 | 适用 |
|---|---|---|
| **仓库级**（默认） | `Docs/` 或 `docs/` | 单主题项目、HYmd 等 |
| **主题级** | `docs/{主题}/` 或 `Docs/{主题}/` | 大仓多主题（如 hy-cad-tool 的 `docs/FiniteElement/`） |

**大小写**：以仓库既有约定为准（`Docs/` 与 `docs/` 均可，不强制统一）。

**选定规则**：
- 用户 `@` 了具体主题目录 → 在该主题目录套用本结构
- 用户说「初始化文档」且仓库已有 `docs/` 多主题 → 问清主题名，在 `docs/{主题}/` 创建
- 单主题小项目 → 仓库根 `Docs/` 或 `docs/` 一套即可

下文用 `{DOCS}` 代指上述任一根路径（如 `Docs/`、`docs/FiniteElement/`）。

## 使用方式

当用户触发以下场景时，**必须**按本 skill 执行：

| 触发词 / 场景 | 动作 |
|---|---|
| 「初始化文档」「建立文档结构」「搭建 Docs」 | 在 `{DOCS}` 创建全套骨架（6 核心文档 + 5 子目录） |
| 「更新日志」「同步状态」「更新文档」 | 更新 `03-实施与状态`；核心逻辑/架构/启动流程变化时连带更新 01/02/04；本次有「多轮才通过」的经验则追加写入 05；**不**改 06（帮助文档仅显式触发） |
| 「记经验」「踩坑记录」「整理实现细节」「记到 05」 | **只**更新 `05-经验教训.md`（先过判定门槛，按主题追加条目，不新建平行文件） |
| 「生成帮助」「更新帮助」「用户手册」「帮助文档」 | 按 **L0-project-help-doc** 只写 `{DOCS}/06-帮助文档.md`（本 skill 不代写） |
| 「完善启动文档」「发行路径」「打包用时」「步骤用时」等 | **只**更新 `04-启动与测试.md`：命令放代码块、成品路径、**逐步用时估计**（见下方「04 写法约束」） |
| 竞品调研、产品对比、市场调研 | 写入 `{DOCS}/Research/`，**不**在根目录新建文档 |
| 概念学习、技术笔记 | 写入 `{DOCS}/Learning/`，**不**在根目录新建文档 |
| 阶段设计、执行计划、MVP 蓝本 | 写入 `{DOCS}/Plan/`，**不**堆在根目录 |
| 金标准评估、阶段结案记录 | 写入 `{DOCS}/Evaluations/` |
| 用户有明确项目目标（立项/开工） | 优先完善 `01-核心逻辑.md` + `02-项目架构.md`，再补 03/04 |

## 目录结构（固定）

```
{DOCS}/
├── README.md              # 文档导航 + 使用方法
├── 01-核心逻辑.md          # 人类阅读：为难谁、给谁用、什么机制、边界在哪（活文档）
├── 02-项目架构.md          # AI 阅读：模块职责、目录映射、数据流、关键决策（活文档）
├── 03-实施与状态.md        # 阶段、版本快照、最近变更、下一步、已知问题（活文档）
├── 04-启动与测试.md        # 启动、编译、测试、发行；命令全在代码块（开发者向）
├── 05-经验教训.md          # 只记多轮修改才通过的工程经验（活文档）
├── 06-帮助文档.md          # 【可选】最终用户手册；由 L0-project-help-doc 独管
├── Research/              # 竞品与产品调研
├── Learning/              # 概念学习笔记
├── Archive/               # 过期文档归档
├── Plan/                  # 具体执行计划与阶段设计
└── Evaluations/           # 金标准评估与结案记录
```

### 人类阅读 vs AI 阅读（01 与 02 的分工，必读）

同一个项目要同时服务两类读者，写法不同，不能混在一篇里：

| | 01-核心逻辑（给人读） | 02-项目架构（给 AI 读） |
|---|---|---|
| 回答什么 | 这软件在干什么、为难谁、凭什么这么设计 | 模块在哪、数据怎么流、改功能该动哪个文件 |
| 写法 | 结论先行、对比表、允许类比与口诀帮记忆 | 结构化表格、路径精确到文件、命名与代码一致 |
| 禁止 | 堆源码路径、接口签名、行级细节 | 类比、比喻、模糊指代（如「那个模块」「相关文件」） |
| 更新时机 | 产品定位 / 机制 / 边界变化时 | 模块 / 路径 / 数据流 / 选型变化时 |

**判别法**：一段内容删掉后「新用户看不懂产品」→ 归 01；删掉后「AI 改码找不到位置」→ 归 02。

### 核心文档 vs 子目录分工

| 层级 | 更新频率 | 内容粒度 | 示例 |
|---|---|---|---|
| **01~04** | 高（「更新日志」按需同步） | 摘要、快照、当前真相 | 03 写「P1.v0.3 完成，15/15 测试全绿」 |
| **05** | 中（多轮才通过的问题定稿后追加） | 弯路与定稿方案的对照 | 05 写「警告框：曾走主题 blockquote 三轮失败，定稿 `data-hymd-alert` + decorate 时机」 |
| **06**（可选） | 低（仅「生成/更新帮助」时） | 用户怎么用；推荐流程 + 等价操作 | 见 L0-project-help-doc |
| **Plan/** | 低（阶段启动/定稿时写） | 详细设计、接口伪码、验收清单（**前瞻**） | `03-阶段1收尾与接口化-…` |
| **Evaluations/** | 阶段结案时写一次 | 五维评分、证据、结论 | `E001-HYFEA-P0v0.1-…` |
| **Research/** | 调研完成时追加 | 长篇对标、决策论证 | `001-自研通用FEA的第一性原则重审-…` |
| **Learning/** | 学习笔记追加 | 概念深度学习 | `00L1-FEA数学基础深入学习-…` |

**禁止**：把状态快照写进 Plan/ 或 Research/ 替代 03；Plan/ 文档带日期可以，但 03/05 不允许带日期平行版本。

### 各文档与其它 Skill 的边界（必读）

| 写哪里 | 写什么 | 不写什么 |
|---|---|---|
| **01-核心逻辑** | 问题陈述、目标用户、机制模型（不展开实现）、硬边界与口诀 | 源码路径、实现细节、启动命令、试错过程 |
| **02-项目架构** | 模块职责、目录映射、数据流、关键决策一句话理由 | 行级细节、试错过程、用户故事 |
| **03-实施与状态** | 阶段划分、版本快照、最近变更、待办优先级、已知问题与风险 | 已定稿工程经验（归 05）、启动命令（归 04） |
| **04-启动与测试** | 开发者如何跑起来、如何验收、**发行/打包步骤**；命令全放代码块；长步骤写**用时估计**与（若本机固定）**绝对路径成品** | 经验教训（归 05）、产品逻辑（归 01） |
| **05-经验教训** | **多轮修改才通过**的问题：弯路清单 + 最终正确做法 + 禁令 | 一次通过的常规实现、待办、状态百分比、概念科普 |
| **06-帮助文档**（可选） | 最终用户怎么用；推荐流程 + 等价操作表；由 **L0-project-help-doc** 独管 | 编译命令、源码路径、实现细节；不随「更新日志」改 |
| **Plan/** | 还没做完或下一阶段怎么做 | 已落地的「当前正确做法」（定稿后提炼进 05） |
| **Learning/** | 通用概念、框架原理笔记 | 本仓库特有的坑（归 05） |
| **Research/** | 产品/UX/竞品决策 | 代码级实现备忘 |
| **pitfalls Skill** | 可检索的踩坑症状 + 正确做法（跨项目强制闭坑） | 完整上下文（pitfalls 可链到 05 条目） |
| **Transcript/**（若有） | 原始对话/检测报告存档 | 不要当「当前真相」；定稿后摘要进 05 |

**05 写入时机与判定门槛**：该问题是否经历「首次尝试失败 → 多轮修改 → 最终通过」？是（无论人为失误还是 AI 失误）→ 记；否（一次就做对）→ **不记**，记了只会稀释检索价值。

**05 条目粒度**：一个难啃问题 = 一条；同主题再次踩坑 → **原地增补**该条，不新建平行标题堆叠。

## 文档写作硬约束（对本 skill 产出的全部 Markdown 生效）

以下约束适用于按本 skill 新建与修改的**每一份**文档（README 不豁免）：

1. **术语首现解释**：术语或缩写在本文档首次出现时，紧跟「是什么＋起什么作用」，缩写给全称；表格内首现也在该格解释；再次出现不重复；跨文档重新计首次。
2. **节首结论先行**：每节先给结论，再讲支撑事实与约束；不为形式完整而下钻。
3. **证据级别标注**：关键结论标明 **已验证 / 推断 / 建议 / 待验证**（结论处标明即可；文档尾部可汇总一行）。
4. **交付前自检**：以上三点逐一过检，不通过先改再交，不得以「命令能跑」交卷；自检内部完成，不输出过程。
5. **写完必须过 L0-02 自检**：交付前加载并执行项目 skill `L0-doc-terminology-gate`（术语 / 证据 / 结论先行门闩；不替代 alwaysApply 的 L0 rules）。

### 扩展规则

- 固定 **5 个子目录**：`Research/` / `Learning/` / `Archive/` / `Plan/` / `Evaluations/`（初始化一律建齐）
- 总数 **恰好 5 个**；禁止另开第 6 个子目录
- 根目录文件：固定 6 个核心文档（README + 01~05）；**可选**第 7 个 `06-帮助文档.md`（由 L0-project-help-doc 管理，初始化时不创建）；禁止第 8 个及以上文件


## 触发协议详解

### 1. 初始化文档

**前置**：确认 `{DOCS}` 路径（仓库级 or 主题级），检查目标目录是否已存在。

**步骤**：
1. 创建 `{DOCS}/` 及固定 5 个子目录（Research / Learning / Archive / Plan / Evaluations）
2. 按下方模板创建 6 个核心文档（已有则跳过，不覆盖用户内容）
3. 在 `README.md` 写入导航表（含全部 5 个子目录）
4. 若项目已有 `Doc/`（单数）或平铺旧文档，**不自动迁移**；在 README 注明历史文档位置

**核心文档首版内容**：
- 有 Plan/Research 等现成来源 → **提炼真实内容**填入 01~04（非空模板）；05 可先骨架，有多轮定稿的坑再填
- 无来源 → 套骨架模板，README 中链接到已有子目录文档

### 2. 更新日志

用户说「更新日志」时，**必须更新** `03-实施与状态.md`（基于当前会话/近期改动，**并对照代码与测试实际状态**），其余按需；**不**更新 `06-帮助文档.md`（帮助仅由 L0-project-help-doc 在显式触发时写）：

| 文档 | 更新内容 |
|---|---|
| `03-实施与状态.md` | 本次完成的功能、修复、决策 → 「最近变更」；未完成项移入「下一步计划」；调整优先级；更新版本快照与已知问题 |
| `01-核心逻辑.md` | **仅当**产品定位/机制/边界有变化时更新 |
| `02-项目架构.md` | **仅当**模块/路径/数据流/技术栈有变化时更新 |
| `04-启动与测试.md` | **仅当**启动/编译/测试/发行命令有变化时更新；涉及长流程时同步核对**用时估计**（有实测则改数字） |
| `05-经验教训.md` | **仅当**本次有「多轮才通过」的问题定稿时追加条目 |
| `06-帮助文档.md` | **不在本协议内**；用户说「生成帮助 / 更新帮助」时由 L0-project-help-doc 处理 |

**禁止**：
- 新建 `03-实施与状态-2026-07-08.md` 等带日期的平行文档
- 把状态更新写进 Research/ 或 Learning/
- 每次更新都改 01/02/04/05（无变化则不动）
- 把完整聊天记录贴进 05（只提炼弯路对照与最终方案）
- 因「更新日志」顺带改 `06-帮助文档.md`（帮助仅显式触发）

**版本行**：每次更新后，修改对应文档尾部的 `**版本** | **更新**` 行。

### 3. 记录经验教训（05 专用）

用户说「记经验」「踩坑记录」「整理实现细节」「记到 05」等时：

1. **过判定门槛**：该问题是否经历「首次尝试失败 → 多轮修改 → 最终通过」？否 → 告知用户不入 05（可提议写 02 或不记）
2. 确认最终方案已在代码中落地（未落地 → 先问是否仍要记「当前已知正确做法」并标 待验证）
3. 打开 `{DOCS}/05-经验教训.md`
4. 查重：已有同主题条目 → **原地增补**；否则在「经验条目」下追加二级标题
5. 按条目模板填写（见下方 05 模板）
6. 更新文档顶部「索引表」一行 + 尾部版本行
7. 若属可跨项目复用的坑 → **另**按 pitfalls 规则写入 pitfalls Skill，并在 05 条目中互相链接

**禁止**：新建 `05-xxx.md`、把同一条经验再抄一份进 Learning/、把未定稿试错过程当最终方案、记录一次就做对的常规实现。

### 4. 调研与学习

- 调研 → `{DOCS}/Research/编号-标题-YYYY-MM-DD.md`
- 学习 → `{DOCS}/Learning/编号-主题.md`
- 编号从该目录现有文件最大编号 +1 起算
- 内容再长也不拆成多个根目录文档

### 5. 归档

核心文档大改版前：
1. 将旧版全文复制到 `{DOCS}/Archive/原文件名-归档-YYYY-MM-DD.md`
2. 在原文件原地写入新版内容
3. **不**保留两个活跃版本

**04 写法约束**（启动 / 编译 / 发行）：

1. **命令一律放 fenced 代码块**：所有可执行命令必须放在代码块中，便于整块复制执行；**表格内不放可执行命令**（表格只写步骤名、用时、时机，命令在对应代码块给出）。
2. **长步骤必须写用时**：凡预计 **≥ 1 分钟** 的命令（`npm ci`、`compile`、`gulp`、大目录拷贝、语言包首次下载等），在用时总览表标注参考区间（如 `5–10 分钟`）；有本机实测则写「实测约 X 分钟」。
3. **用时总览优先**：发行/全量构建多步时，先给「步骤 | 参考用时 | 何时必跑」表，再展开复制用命令块。
4. **成品用绝对路径**：便于复制黏贴；注明工作目录仓库（防混仓，如 HYmd vs hymd-code）。
5. **区分完整路径 vs 增量路径**：写清「首次/换分支要跑哪些」「日常可跳过哪些」（例如依赖已好可只跑 gulp）。
6. **成功判据**：长任务写一句成功标志（如 `Finished 'vscode-win32-x64-min'`），避免把 warn / funding 提示当成失败。
7. **用时来源**：优先会话实测或近期本机记录；无数据时给保守区间并注明「视机器/磁盘/网络浮动」；禁止编造精确到秒的假数据。
