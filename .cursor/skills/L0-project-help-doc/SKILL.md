# 项目帮助文档编写

> **结论先行**：本 skill 只管 `{DOCS}/06-帮助文档.md`——面向最终用户/小白写「怎么用」；只在用户显式要求时生成或更新，兼做体验走查。

`{DOCS}`（文档根路径）与 `L0-project-docs-structure` 一致：仓库级 `Docs/`/`docs/`，或主题级 `docs/{主题}/`。

---

## 何时应用（仅显式触发）

| 触发词 | 动作 |
|---|---|
| 「生成帮助文档」「生成帮助」 | **首次全量**：按模板写完整 06；走查全部可操作功能 |
| 「更新帮助」「用户手册」「帮助文档」 | **增量**：只改入口/流程有变化的功能节；走查涉及功能 |

**不触发**：用户说「更新日志」「同步状态」「更新文档」——那是 `L0-project-docs-structure` 管 01~05；本 skill **绝不**因更新日志而改 06。

**反向**：开发者启动/编译/发行 → `04-启动与测试`；实现细节 → `02`；踩坑经验 → `05`。

---

## 落点与命名

| 项 | 规则 |
|---|---|
| 路径 | `{DOCS}/06-帮助文档.md` |
| 更新方式 | 固定单文件，**原地更新** |
| 禁止 | `06-xxx.md` 平行文件、`Help/` 目录、带日期的平行版本 |

06 是 `L0-project-docs-structure` 根目录的**可选第 7 个文件**，由本 skill 独管；初始化文档时**不**自动创建，首次「生成帮助」时再建。

## 模板（初始化/首次生成时套用）

```markdown
# 帮助文档（用户手册）

> 面向最终用户 / 小白。写「怎么用」；开发者启动见 [04-启动与测试](04-启动与测试.md)，产品逻辑见 [01-核心逻辑](01-核心逻辑.md)。
> 触发：「生成帮助」「更新帮助」；不随「更新日志」自动改。

## 1. 这是什么 / 适合谁

{一两段：产品是什么、给谁用、能做什么}

## 2. 五分钟上手（最优默认路径）

1. {从打开软件到完成第一件小事的最短路径}
2. …
3. …

## 3. 推荐日常工作流

{日常使用的最优顺序；可含编号步骤}

## 4. 功能操作详解

### {功能名}

- **目标效果**：{用户想得到什么}
- **推荐流程**：
  1. {步骤}
  2. {步骤}
- **等价操作**（达到相同效果）：

| 入口 | 步骤 |
|---|---|
| 右键 | … |
| 快捷键 | … |
| 菜单 / 其它 | … |

- **注意**：{可选：易错点、作用域、与相近功能区别}

## 5. 常见问题（用户向）

| 现象 | 解决 |
|---|---|
| {用户会撞到的} | {可执行步骤} |

## 6. 快捷键速查（可选）

| 快捷键 | 作用 |
|---|---|
| {键} | {作用} |

---

**版本**：v1.0 | **更新**：{YYYY-MM-DD}
```

更新时**只改各节内容**；可在「功能操作详解」下按功能追加 `###` 节，不删改既有章节骨架。

---

## 写法约束

1. **每功能节必须有**：一条**推荐流程**（最优默认路径）+ **等价操作**表；推荐流程只留一条，发现成本最低、新手最稳。
2. **只写实测可用入口**（证据级别：已验证）：菜单名、快捷键、按钮以当前界面为准；无第二入口则表中写「暂无」并标日期；**禁止臆造**未实现入口。
3. **白话**：用界面上看得见的按钮/菜单名；禁止源码路径、协议名、类名、编译命令、实现细节。
4. **术语首现解释**：术语或缩写首次出现时紧跟「是什么＋起什么作用」，缩写给全称；表格内首现也在该格解释。
5. **节首结论先行**；关键结论标 **已验证 / 推断 / 建议 / 待验证**（入口可用性默认要求已验证）。
6. **不写进 06**：开发者启动命令、实现细节、竞品对比、待办清单、体验问题清单（体验问题归 03）。

---

## 体验走查（生成/更新时必做）

写作过程即用户体验复核：

1. 按拟写/拟改的**推荐流程**实际走一遍界面（能跑就跑，不能跑则对照当前 UI 截图/代码确认入口是否真实存在）。
2. 发现坏入口、别扭流程、缺提示、易错点 → **记入** `{DOCS}/03-实施与状态.md` 的「已知问题与风险」，**不**写进 06 正文（06 只写「当前正确怎么用」）。
3. 走查中确认不可用的入口 → 06 中标「暂无」或删除该行，禁止假装可用。

## 触发协议

### 1. 生成帮助（首次全量）

1. 确认 `{DOCS}` 路径；确认产品已有可操作 UI（无可操作功能 → 告知用户并中止，或只写「这是什么」骨架并标待验证）
2. 若 `06-帮助文档.md` 已存在 → 改为走「更新帮助」协议，勿覆盖全文除非用户明确要求重写
3. 列出可独立完成的用户任务（每个任务 = 一个 `###` 功能节）
4. **全功能走查**（见上节）
5. 按模板全量写入 06；每功能节填齐推荐流程 + 等价操作表
6. 走查发现写入 03「已知问题与风险」；更新 03 / 06 版本行
7. 若 README 导航尚无 06 → 补一行（可选文档）

### 2. 更新帮助（增量）

1. 打开 `{DOCS}/06-帮助文档.md`（不存在 → 改走「生成帮助」）
2. 对照本次入口/流程变化：已有同功能 `###` 节 → **原地改**推荐流程与等价表；新功能 → 在「功能操作详解」下追加
3. **只走查本次涉及的功能**；发现写入 03
4. 用户步骤未变、仅底层实现变 → **不要**为了「写过」而改 06
5. 更新尾部版本行

**禁止**：新建 `06-xxx.md` / `Help/`；把开发者启动写进 06；把实现细节写进 06；缺少等价操作表的空功能节；因「更新日志」顺带改 06。

## 与其它文档 / Skill 的边界

| 写哪里 | 写什么 | 不写什么 |
|---|---|---|
| **06-帮助文档**（本 skill） | 最终用户怎么用；推荐流程 + 等价操作 | 编译命令、源码路径、实现细节、体验问题清单 |
| **03-实施与状态** | 走查发现的体验问题 / 已知风险 | 用户操作手册正文 |
| **04-启动与测试** | 开发者如何跑起来、打包发行 | 小白操作说明 |
| **01-核心逻辑** | 产品为什么这样设计 | 点哪里、按哪个键 |
| **L0-project-docs-structure** | 01~05 + 子目录结构；「更新日志」 | 不代写 06；仅承认 06 为可选第 7 文件 |
