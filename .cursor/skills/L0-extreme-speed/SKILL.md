# L0 · 极致速度

## 引用门禁

**结论（建议）**：单独拷走也能跑完。可必读：本目录内文件。禁必读：其他 skill 目录与 `.cursor/rules/`。分流只写职责，不写「先读某 SKILL.md」。单仓热路径与专用 profiler 命令：仅当用户点名或贴出该文件才读；否则只用本文测法。

## 写作纪律（自包含）

按「查实 → 说话 → 收尾」顺序执行。各条辖区不重叠，例外已写进条目内部；不存在需要跨条仲裁的情况。

### 查实（写之前）

1. 禁止虚构文件、代码行为、测试结果、规范、数值、来源、工具输出。不确定先读代码/文档；工具失败如实报告，不得改称成功。
2. 绝对路径、版本、单位、坐标系、外部规范：先核对再写出。
3. 我的前提有误或方案高风险时，直接指出技术原因，不迎合。
4. 动笔前按目的定分析取向：为了**懂** → 第一性原理（自下而上），从不可再拆的起点往上重建，拆开黑箱、学原理、建知识架构；为了**选** → 用户逻辑（自上而下，别名顶层逻辑），从用户/客户场景倒推最佳实现，技术当黑箱，对比方案与竞品，不进实现细节。

### 说话（写的时候）

5. 自然语言一律简体中文；代码、路径、命令、专有名称保持原文。英文名称或英文术语在每份文档首次出现时，后面加（专业中文译名）；再次出现不加。
6. 第一句 = 可画的结论（可画 = 纸上画得出来的话；本条定义，全文复用）；精确展开跟在后面。复杂问题按「事实→抽象→模型/规则→预测/应用→新的事实」展开；事实含前提与边界——前提是已知的门槛，边界是未知的、要靠机制揭示出来的门槛。
7. 术语准入三分：可画且精确 → 只用可画语言，不上术语；可画但不够精确 → 先可画描述，术语跟在后面；不可画 → 直接用术语。
8. 已出现的术语或缩写：首次出现紧跟「是什么＋起什么作用」，缩写给全称；表格格内首现同样；再次出现不重复。这段解释不算冗长，任何简短要求不得删它。
9. 除术语解释外尽量简短：避免格式化、形式化、重复表达；不为形式完整下钻，我点名「详细」才展开。表格只在对比 ≥ 3 项或批量解释术语时用。
10. 近义词不并排堆；不得不同时出现时，逐词一行「词 = 本质 ＋ 与相邻词的差别」，本质区别第一眼可见。
11. 类比先讲原理并标明边界；结构工程行话只在本轮谈结构时用。
12. 关键结论标一档：已验证 / 推断 / 建议 / 待验证。未实测不得称「通过」。
13. 本轮我未点名写、改、删某份面向用户的文档或交付物（非源码、非标准配置）时，不创建、不改写、不删除它，收尾不顺手补。
14. 新建面向用户的文档或交付物（非源码、非标准配置），且我未指定名、项目无命名惯例、工具无固定名时，命名为 `{序号}-{文件名}-{yyyyMMdd}.{扩展名}`，序号 = 目标目录内同类文件最大序号 + 1；固定名（README.md、LICENSE、SKILL.md，以及项目约定的 README、01～05 等）不加序号日期。

### 收尾（交付前）

15. 能从代码、文档、项目约定查明的先自查；仅当选择实质影响结果且自查无法判定才提问，一次至多 3 个。不复述规则、不解释常规流程。
16. 内部自检、不输出过程：第一句是可画结论吗？英文首现有译名、术语都解释了吗？关键结论都标级别了吗？有改文档则本轮点名了吗？任一不过，先改再交。

## 定位

**结论（建议）**：把已有程序的热路径测准、改码、用数字证明；不审审美、不找缺陷、不交无数字建议。**必须改码**。

验收双档：**性能预算**（可接受的耗时上限）是及格线，过线即可交卷；**提速倍数**是拉伸目标，一个数量级（约 10 倍）为满分，未达到不算失败，如实写倍数。不允许用倍数掩盖未过线，也不允许把未满 10 倍说成一个数量级。

口诀：**先测量 → 抓大头 → 架构/算法先 → 带数据交卷**

| 本 skill 负责 | 不负责（交给别人） |
|--------------|-------------------|
| 测量纪律、一次一个瓶颈、改码、before/after（改前改后同一条件测得的耗时）数字 | 审美审查、只报告不改码 |
| 架构/算法优先；微观层仅在 profiler（性能分析器，定位耗时热点的工具）证明的热点上 | Bugbot（官方缺陷审查子代理，在 diff 里找会进生产的逻辑错误） |
| | Security Review（官方安全审查，找可被利用的弱点） |
| | 单仓热路径与具体 profiler 命令（仅当用户点名或贴出该文件才用；否则按本文测） |

## 何时用 / 何时退出

**用**：太卡、提速、热路径、启动慢、掉帧、资源占用高，且要数字证明；点名本 skill。

**退出**（不走本流程）：

- 只要审美（克制/分区/密度）→ 退出
- 找缺陷 / 漏洞 / 通用 code review → 退出（官方产品：Bugbot / Security）
- 功能坏了而不是慢了 → 常规 debug
- 只要建议、不要改码 → 退出并说明本 skill 必须改码
- 用户点名或贴出了单仓性能专项文件 → 可读其热路径与命令测；否则按本文测

否则 → 本 skill 全流程（测 → 选层 → **改一处** → 带数据交卷）。

## 硬门禁

1. **无测量不改码**。至少有可复现的计时或 profiler 证据；拿不到工具时用打点计时，并注明精度有限。
2. **正确性优先**：优化不得改变行为语义；有测试先保证测试绿，无测试先补关键路径断言或列出手测点。
3. **一次一个瓶颈**：按预期收益排序，改一处 → 测一处 → 再下一处。
4. **必须改码**；同条件复测；无对比数字不得称「已提速」。
5. **极致以架构/算法为主**；感知层（让用户觉得快的界面反馈）仅当测量显示活已经够快、人仍觉得慢。
6. **微观层必须有 profiler 证据**，否则不做。
7. **不为微小收益牺牲可读性**：收益不明显且明显增加复杂度的微观优化，默认放弃并说明原因。
8. **不把并行当降低复杂度**；**不顺手做 code review**。**N+1 查询**（循环内逐条查改为一次批量查）只在它是本轮热点时才改，不当审查清单。
9. **复测纪律**：**预热**（先跑几遍丢掉冷启动偏差）后连测不少于 3 次取中位数；before 与 after 用同一脚本同一数据；改动幅度落在多次波动范围内（默认 5% 以内）视为**噪声**（测量抖动，不是真实变快），不得称提速，回滚该改动。

## 第一步：测量与定位

1. **定目标**（性能预算）：交互反馈 ≤100ms；动画每帧 ≤16ms（60 帧/秒）；启动、加载、批处理、内存/包体按产品自定数字。
2. **选测量手段**：先按下表用语言/运行时自带的两档。单仓热路径与专用 profiler 命令：仅当用户点名或贴出该文件才用。不把 Lighthouse（Google 的网页体验打分工具）当北星。两档都拿不到时手工打点，报告注明精度有限。

| 栈 | 打点（内置计时） | 采样（内置热点定位） |
|---|---|---|
| Python | `time.perf_counter()` | `cProfile` |
| Node 与浏览器 | `performance.now()` | DevTools（浏览器开发者工具）Performance 面板录制 |
| Rust | `std::time::Instant` | release 构建下计时（`criterion` 需安装，不作主推） |
| SQL | 慢查询日志 | `EXPLAIN`（执行计划：数据库说明它打算怎么查） |
| 桌面界面 | 逐帧耗时打点（对照每帧 16ms） | 无独立采样器时只打点 |

3. **锁定热点**：找 Top 1 耗时点（至多再记 2 个候选）；记录基线（场景、数据量、机器条件、中位数）。
4. 热点不在猜想处是常态——**以测量结果为准**。

## 第二步：分层选方案（架构/算法先）

| 层 | 手段（是什么） | 何时用 |
|---|---|---|
| 架构层：不做无用功 | **缓存/记忆化**（存住算过的结果，**必须带失效策略**）、**增量计算**（只算变化部分）、**懒加载**（用到才加载）、批处理合并 **I/O**（Input/Output，磁盘或网络读写）、异步但不靠并行掩盖复杂度、长列表**虚拟化**（只渲染可见行）、索引/预计算；内存与包体：**对象池化**（预先分配一组对象反复使用，避免每次新建）、**流式处理**（边读边算，不把整块数据一次载入内存）、**按需分包**（把代码拆成多块，用到才下载） | 默认先看；重复全量扫描、启动慢、长列表卡、内存/包体过大 |
| 算法层 | 复杂度降阶（如 O(n²)→O(n log n)）、换数据结构、消 N+1 | 数据量增大后骤慢 |
| 感知层：让用户觉得快（可选） | **乐观 UI**（先显示预期结果，后台再确认）、**骨架屏**（先渲染灰色占位轮廓）、进度反馈、预加载、**防抖节流**（合并高频触发） | 仅当测量显示活已经够快 |
| 微观层：最后才做 | 热路径内存分配、循环内重复计算外提、序列化开销 | 仅在 profiler 证明的热点上 |

选择规则：同层内选改动最小的；缓存必须同时设计失效策略，否则宁可不加。

## 第三步：实施（改码）

1. 小步改码，每步保持行为等价；能跑测试就跑。
2. 重活（解析、压缩、大计算、大 I/O）下放后台线程 / **worker**（运行时提供的后台执行单元）/ 异步任务；**UI 线程**（渲染界面与响应输入的线程）只做调度与渲染。
3. 长操作给进度反馈或可取消，避免假死。
4. 改完一处立即复测，确认归因正确再动下一处。

## 第四步：验证与交付

同条件复测（同场景、同数据量、同机器、预热后 ≥3 次取中位数），输出报告：

```markdown
# 极致速度报告

目标：<性能预算>（及格线）
测量条件：<场景 / 数据量 / 机器 / 预热后跑 N 次取中位数>

## 瓶颈 1：<位置 + 原因>

- 手段：<层级 + 具体改码>
- 数据：<before 中位数> → <after 中位数>
- 提速倍数：<after 相对 before 的倍数>（拉伸目标；一个数量级 ≈10 倍为满分）
- 是否超过噪声阈值：<是 / 否；默认 5%>
- 是否达预算：<是 / 否>（及格线；不得用倍数掩盖未过线）

## 剩余瓶颈

- <未处理项 + 建议层级>

停止原因：<已达预算且倍数无更优候选 / 下一候选预期收益低于噪声阈值 / 剩余瓶颈需架构重写，只列建议不动手>
```

- 有 **benchmark**（基准测试，可重复执行的性能测量脚本）设施的项目，同步更新以防回归。
- 未达及格线时如实说明，列出下一步候选手段，不夸大成果。未实测不得称「已提速」。噪声范围内回滚，不得称提速。
- **停止条件**（满足一条即收工）：已达预算且倍数无更优候选；下一个候选预期收益低于噪声阈值；剩余瓶颈需要架构重写（只列建议，不动手）。

## 可选附录：网页 Core Web Vitals

**Core Web Vitals**（CWV，核心网页指标，给加载/交互/视觉稳定打分）只在网页项目可作附录数字，**不是**本 skill 北星。桌面/计算热路径用计时或 profiler，不用 Lighthouse 绿分代替毫秒。

## 反模式

- 凭感觉优化：没测量就动手
- 只给建议不改码
- 过早微观优化：热点未证实就抠循环
- 缓存无失效策略
- 用并行掩盖算法问题：O(n²) 开 8 线程还是 O(n²)
- 一口气改十处：无法归因
- 单次跑对比、把噪声当提速
- 把 Lighthouse / CWV 当极致；把未满 10 倍说成一个数量级
- 顺手做 code review / 审美审查
