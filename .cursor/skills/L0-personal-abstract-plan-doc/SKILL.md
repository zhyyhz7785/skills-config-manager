# 个人高度抽象 Plan 文档

## 定位

> **这是「用户自己用的全局视野文档」，不是「AI 与用户协作执行的实施文档」。**
> **正确、简洁第一；任何不影响全局判断的实现细节都不进入本文档。**

| 维度 | 本 skill（00 总体计划） | 具体执行计划（01/02/…） |
|------|-----------------------|------------------------|
| 目的 | 全局视野、快速浏览 | 落地实施、协作执行 |
| 受众 | 用户自己 | 用户 + AI |
| 篇幅 | **≤ 200 行（硬约束）** | 不限 |
| 程序代码/接口/技术选型表 | **禁止** | 允许 |
| 阶段细节 | 一行一阶段 | 展开 |
| 演化 | 单一活跃文件，原地更新 | 每阶段可重写 |

## 何时应用

用户说：

- 「制定一个总体计划」/「做个 00 计划」/「顶层锚定文档」/「多年路线」/「未来 5 年 / 10 年怎么走」
- 「我自己看的」/「只给我自己」/「用作全局视野」/「高度抽象」/「最简约的抽象」/「提炼精简框架」

**反向触发（不要用本 skill）**：「我们一起来实施」「展开技术方案」「详细排期」「写接口」「列模块清单」——那是具体执行计划（同 `{DOCS}/Plan/` 下 `01-XXX-YYYY-MM-DD.md` 风格），不归本 skill 管。

## 命名与存放位置（对齐 L0-project-docs-structure）

路径规则与 `L0-project-docs-structure` **同一套 `{DOCS}`**（文档根：仓库级 `Docs/`/`docs/`，或主题级 `docs/{主题}/`）。本 skill **只按 L0 级文档结构**落盘与引用：核心文档 README + 01~05、固定子目录 Research/Learning/Archive/Plan/Evaluations；**默认不依赖、不引用 L2 级专属文档**（多数项目目录里只有 L0；遇 L2 仅用户显式点名时才写入 §九「依据」）。

| 字段 | 规则 |
|------|------|
| 编号 | `00`（总体计划永远占 00，且同一 `{DOCS}` 下只有一份活跃文件） |
| 目录 | **`{DOCS}/Plan/`**（docs-structure 固定子目录；若尚无 Plan/，先按 docs-structure 建齐 5 子目录） |
| 文件名 | `00-<主题>-<副标题>.md`（固定名，**不带日期时间戳**） |
| 修订 | **原地更新**；修订历史记在 §十一 修订记录 |
| 归档 | 大改版前旧版复制到 **`{DOCS}/Archive/原文件名-归档-YYYY-MM-DD.md`** |

完整路径示例：`Docs/Plan/00-数据交换总体计划-抽象框架与多年路线.md`（主题级则为 `docs/{主题}/Plan/00-….md`）。

Plan/ 下其它文件命名（`编号-标题-YYYY-MM-DD.md`）见 L0-project-docs-structure；00 是唯一的固定名例外。

## 三条铁律（永久生效，不可妥协）

1. **篇幅 ≤ 200 行** — 含修订记录、图表。超过即重写，不许扩。
2. **禁止细节** — 接口签名 / 程序代码 / 字段定义 / 详细案例 / 大型评分表都不进入。
3. **细节下沉** — 任何阶段、模块、机制的展开，都用一句话指向独立子文档（优先 `{DOCS}/Plan/01-…`、`02-…`，或同 `{DOCS}` 下 Research/Learning 等 L0 文档）。

> 用户原话（verbatim，作为本 skill 立项依据）：
> "**我希望你用最简约的抽象,提炼出精简的框架制定未来多年的框架,和目录结构。**"
> "**这个文档是高度抽象的,需要的是整体框架,正确、简洁是第一位的,不需要任何细节,细节在以后完成。**"
> "**这个 Plan 和你具体执行计划不同,是高度抽象,只给我自己看,用作全局视野快速浏览用的。**"

## 固定 12 节模板（顺序固定；三 / 四 / 六可缺，其余必写）

```text
0. 一句话定位         项目长期定位 + 短期目标
一. 不可变原则        2-4 条，永远不变的工程纪律
二. 目录结构顶层框架   只列稳定顶层，允许"预留位"标注
三. 核心机制精简       （可缺）如双轨/分层/插件机制 — 一图一表搞定
四. MVP 定义           （可缺）MVP（Minimum Viable Product，最小可行产品）：第一个用户可感知产物
五. 验证方法           证明正确的层次 + 不可妥协的铁律
六. 后期预留           （可缺）将来才启用的机制，只列"启用时机"
七. 实施步骤           分阶段，每阶段一行，带"核心交付 + 关键依赖"
八. 长期愿景           1/3/5/10 年只列时间与形态，不写技术
九. 依据与下沉         依据=本计划从哪些 L0 文档/约束得出；下沉=细节交给哪些 Plan/01… 子文档
十. 本文档使用约定     强制"只写框架 / ≤200 行 / 细节下沉 / 原地更新"
十一. 修订记录         版本表
```

## 表达密度（每节上限）

| 节 | 内容上限 |
|----|---------|
| 0 定位 | 1-2 句 |
| 一 原则 | 每条 1 段（2-4 行） |
| 二 目录 | 1 个目录树代码块 + 1 段"依赖方向"约束 |
| 三 机制 | 1 个 mermaid（文本语法绘图工具）示意图 + 1 张 ≤5 行表格 |
| 四 MVP | 1 张 5-7 行表格 |
| 五 验证 | 1 张 3-5 行表格 + 3 条铁律 |
| 六 预留 | 1 张 4-6 行表格 |
| 七 步骤 | 1 个 mermaid + 1 张 ≤7 阶段表格 |
| 八 愿景 | 1 张 4 行表格 |
| 九 依据与下沉 | 1 张表格（依据 / 下沉两栏；依据默认只列 L0 文档） |
| 十 约定 | 1 张 4 行表格 |
| 十一 修订 | 1 张表格 |

**全文 mermaid 总数 ≤ 3 个；表格总数 ≤ 8 张。**

## 禁写清单（看到就停手）

| 类别 | 禁写示例 |
|------|---------|
| 程序代码 | 任何 csharp / python / cpp / yaml 等程序代码块 |
| 接口 | `public interface IXxx { ... }`、`struct`、`record` 定义 |
| 字段 | `Id : string`、字段类型表 |
| 算法伪代码 | 求解器 / 评估器 / 路由器的实现伪代码 |
| 案例清单 | 具体案例编号清单（如 `T1-001 ~ T1-005`） |
| 大表格 | 多于 5 行的属性 / 维度 / 评分表 |
| 引用链 | 跨文档的复杂依赖图 |

**允许**：`text` 目录树与纯文本结构示意块（§二必用）、mermaid 示意图（全文 ≤ 3 个）。凡发现禁写内容，**立刻删除并替换为一句话**："详见 `[XXX](path)` 第 X 章 / 第 X 节"。

## 完整执行流程（给 AI Agent，共 5 步）

### Step 1 — 对齐 4 个参数

向用户回显确认（未明确则按对话推断，路径选定规则与 L0-project-docs-structure 相同）：

| 参数 | 用途 |
|------|------|
| 主题 | 文件名主标题 |
| 副标题 | 文件名副标题 |
| `{DOCS}` | 仓库级 `Docs/`/`docs/`，或主题级 `docs/{主题}/`；决定落点 `{DOCS}/Plan/` |
| 依据文档清单 | §九用；**默认只列同 `{DOCS}` 下的 L0 文档**（01~05、Research/、Learning/ 等） |

若 `{DOCS}/Plan/` 不存在 → 先按 docs-structure 补建固定 5 子目录，再写 00。

### Step 2 — 需求 1:1 映射

读用户消息，把原始需求逐条标号并映射到模板节（如「模块化原则」→ 一；「核心机制」→ 三；「最小产物」→ 四；「阶段划分」→ 七）。
**用户每一条原始需求都必须落在模板某节；没落上的需求 → 主动询问用户**。

### Step 3 — 撰写，每节自检

- 当前总行数（含本节）≤ 200？超了回头精简前面
- 触犯「禁写清单」？有就删
- 细节留下了？换成"详见 [XXX](path)"（路径落在 `{DOCS}` 下）
- 节首结论先行？术语首现已解释（是什么＋起什么作用，缩写给全称）？
- §九 依据是否误塞了 L2 专属文档？（默认不写；用户显式要求除外）

### Step 4 — 交付前自检

```text
[ ] 落点是 `{DOCS}/Plan/00-<主题>-<副标题>.md`（固定名，无时间戳）；大改版旧版已入 `{DOCS}/Archive/`
[ ] `{DOCS}` 选定规则与 L0-project-docs-structure 一致（仓库级 or 主题级）
[ ] 编号是 00（不是 001 / 01）
[ ] 总行数 ≤ 200
[ ] 12 节齐（允许缺三 / 四 / 六，其余必有）
[ ] mermaid 总数 ≤ 3；表格总数 ≤ 8
[ ] 无程序代码 / 接口定义 / 字段表（目录树 text 块除外）
[ ] 用户每条原始需求都已覆盖
[ ] §九 依据默认仅为 L0 文档（未擅自引入 L2）
[ ] 节首结论先行；术语首现已解释；关键结论已标 已验证/推断/建议/待验证
[ ] §十"使用约定"含"只写框架 / ≤200 行 / 细节下沉 / 原地更新"
[ ] §十一"修订记录"已更新本次版本行
```

### Step 5 — 交付时简要告知用户

只说三件事：完整路径（含 `{DOCS}/Plan/`）；12 节结构（简短列出）；下一步建议（通常是在同 Plan/ 下发起 `01/02` 具体执行计划）。

## 反例（对照学习，通用化）

| 反例 | 错在哪 | 应改为 |
|------|--------|--------|
| 写接口定义 `public interface IXxx<TIn, TOut> { ... }` | 程序细节进了 00 | "每个模块输入输出有明确契约，可被符合契约的实现替换。具体接口见 [Plan/01-…] 第 X 章" |
| 把 10+ 行评分 / 维度大表整张搬入 | 细节表格挤占全局视野 | "多标准评估 → 详见 [子文档] 第 X 章" 一句话 |
| 阶段表写周数 / 人天 / 类名 / 方法数 | 排期与实现细节 | "阶段 1 - 核心交付一句话 - 依赖阶段 0" |
| 落点写成任意自定义目录、或引用整棵 L2 文档树作依据 | 与 docs-structure / L0 默认范围脱节 | 落 `{DOCS}/Plan/`；依据默认只列同树 L0 文档 |

## 与已有 skill 的边界（仅 L0）

| 已有 skill | 区别 |
|-----------|------|
| `L0-project-docs-structure` | 管 `{DOCS}` 结构、子目录与 Plan/ 命名；本 skill 管 **00 内容与写法**（00 固定名是其命名规则的唯一例外）；路径必须复用其 `{DOCS}` |
| `L0-project-help-doc` | 管可选 `06-帮助文档.md`（用户怎么用）；本 skill 不管帮助 |
| `L0-first-principles-learning` | 学习外部知识沉淀；本 skill 是自身项目顶层规划 |

不把 L2 级 skill / 文档树写进本 skill 的默认流程或边界表。
