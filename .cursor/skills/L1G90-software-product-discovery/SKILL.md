# 软件产品调研 → 实现路径规划

在为某个功能「从零做一款软件」之前，先把**做什么**和**怎么做**想清楚。本 skill 把流程固化为 5 个阶段，最终落盘一份调研报告。

* **范围**：模式 A 到「最优实现路径 / 技术方案规划」为止，**不写实现代码**；模式 B 到「方案对比 + 选定 + 最小实现」为止，**可改代码**。

* **语言**：全程简体中文；代码、路径、命令、专有名称保持原文（L0-01）。

* **诚信**：竞品、价格、版本、活跃度等事实**必须来自联网搜索或只读核对**；查不到标 **待验证**，**禁止编造**（L0-03）。

***

## 硬门禁与优先级（落盘前必读）

**结论**：本 skill 的阶段清单与报告模板**从属于**仓库常驻 rules；模板填不满可以，**写作/证据自检不过禁止落盘**。

### 优先级（高 → 低）

```text
L0-02（术语首现 / 节首结论 / 证据级别）
  > L0-03（禁虚构；已验证|推断|建议|待验证；路径版本先核对）
  > L0-01（结论先行；不为形式完整下钻；未要求详细则简短）
  > L0-04（少排版；提问≤3；先自查；不复述 rule 全文）
  > L0-05 + L0-project-docs-structure（落盘目录与命名）
  > 本 skill 流程 / 模板完整度
```

L0-02 与 L0-01 / L0-04 冲突时，**以 L0-02 为准**。

### 写作门禁（对齐 L0-01 / 02 / 03）

1. **节首结论先行**：文首「总论」与每个 `##` 节先给结论，再写支撑事实；不为凑齐模板章节而注水。
2. **术语首现解释**：术语或缩写在本文档首次出现时，紧跟「是什么＋起什么作用」，缩写给全称；**表格格内首现也在该格解释**；再次出现不重复。
3. **证据级别**：关键结论标明 **已验证 / 推断 / 建议 / 待验证**（结论处标明即可）。未实测不得称「通过 / 应已通过」。
4. **详略**：默认短报告、以能判断取舍为上限；**仅当用户明确要求「详细 / 细致」**时加长。
5. **禁止**用「阶段清单已打勾 / 模板章节齐全 / 命令能跑」代替上述验收。
6. 交付前**内部**过 L0-02 三点自检；**不向用户输出自检过程**；报告与聊天**不粘贴 rule 全文**（L0-04；用户质疑遵守或要求审改规则时除外）。

### 与各 L0 / 文档结构的消解

| 来源 | Skill 如何遵守 |
|---|---|
| L0-01 | 默认短文；阶段 2 以表+一行总评为主 |
| L0-02 | 模板强制节首结论与术语示例；自检阻断项 |
| L0-03 | 统一四档证据；禁止「待核实」作为唯一标签（查不到用 **待验证**）；版本/价格/路径先核对 |
| L0-04 | 阶段 0 能自查则标「假设」；实质分歧才问且一次≤3；短表服务对比与术语 |
| L0-05 + L0-project-docs-structure | 竞品/立项调研写入 `{DOCS}/Research/`；命名见阶段 5；**不**以 `product-discovery/` 为默认（避免第 6 子目录） |

## 模式 B：现有产品 UI / 交互专项（轻量）

**结论**：模式 B 流程更短，**不豁免** L0-01/02/03（节首结论、术语首现、证据级别照样做）。

**何时用**：产品/扩展已存在；用户反馈「显示效果差」「切换入口不明显」；需在 **2–5 个 UI 方案** 间选型并落地。不重走完整竞品立项，但**仍须联网查 3+ 参考**（同类 IDE/编辑器怎么放按钮）。

**与模式 A 的区别**：

| | 模式 A（立项） | 模式 B（UI 专项） |
|---|---|---|
| 范围 | 整款产品 | 单个控件/布局/切换流 |
| 竞品数量 | 5–12（清单可多，正文深写少） | 3–6 个参考实现 |
| 产出 | `{DOCS}/Research/` 调研报告 | 对比表 + 可选短 memo；**直接改代码** |
| 权重 | 五维按阶段 0 | **易用 40% + 与宿主一致 30% + 功能 20% + 实现成本 10%** |

**工作流（复制推进）**：

```
- [ ] B0：锁定「谁在哪一步要做什么」+ 宿主约束（VS Code / WPF / Web…）
- [ ] B1：联网查 3+ 参考（官方文档优先：如 VS Code editor/title、Markdown 预览）
- [ ] B2：列 2–5 个候选方案，按 B 权重打分
- [ ] B3：选最优 + 写清「不选其余方案的原因」一句（节首先给推荐结论）
- [ ] B4：最小实现 + 目视验收标准（1–3 条）；未实测不称「已通过」
```

**方案对比表模板**（UI 专项必用；表内术语首现须解释）：

| 方案 | 做法 | 易用 | 宿主一致 | 功能 | 成本 | 加权 | 结论 |
|---|---|---|---|---|---|---|---|
| A | … | /5 | /5 | /5 | /5 | | |
| B | … | | | | | | **推荐** |

**HyMD 已验证样例（2026-07）**：

| 需求 | 候选 | 结论 |
|---|---|---|
| 整篇 WYSIWYG ↔ 源码 | 状态栏 / 命令面板 / **editor/title 图标** / webview 内嵌 | **editor/title**（与 Markdown 预览同位，可发现性最高） |
| sheet 块 预览 ↔ 块体 YAML | Crepe 原生 Copy 栏 / 块工具栏「源码」 / 双击块 | **块工具栏「源码↔预览」** + 修复 Crepe DOM 装饰（`.milkdown-code-block`） |
| 块卡片未渲染根因 | 只查 `pre code` | Crepe 用 `div.milkdown-code-block`，须双路径采集 |

**模式 B 落盘（可选）**：短 memo 写入业务仓既有核心文档一节，或 `{DOCS}/Research/` 短文；**禁止**新建 `{DOCS}` 下第 6 个子目录（如 `product-discovery/`）。用户只要改 UI 时，以代码 + 简短结论回复即可（结论先行、术语首现）。

## 阶段 0：锁定目标与约束（搜索前必做）

**结论**：不先锁定目标就开搜 = 方向跑偏；缺项先自查再给默认并标「假设」，勿连环追问（L0-04）。

先对齐下列项；用户没说的，**给出合理默认并显式标注「假设」**。仅当选择实质影响结果且自查无法判定时提问，**一次至多 3 个**。

| 项 | 要确认什么 |
|---|---|
| 核心功能 | 一句话说清「这款软件帮谁，解决什么问题」 |
| 目标用户 | 谁用、专业度、规模、付费意愿 |
| 平台形态 | 桌面(Win/Mac/Linux) / Web / 移动(iOS/Android) / 浏览器插件 / CLI / 库·SDK（Software Development Kit，软件开发工具包）/ CAD·IDE 插件 |
| 关键约束 | 开源还是商业、预算与人力、时间窗口、技术栈偏好、离线/在线、合规要求 |
| 成功标准 | 怎样算「做成了」（可给默认假设） |
| 五维权重 | 按目标定权重（工具类→易用性高；金融/医疗→安全高；高频生产→稳定高），合计 100% |

**输出**：一段「目标陈述」+ 一张五维权重表。

## 阶段 1：竞品搜索（强制联网）

**结论**：形态要搜全，正文不必写全；清单可宽，深写留给阶段 2 的头部竞品。

用 `WebSearch` 系统性搜索，**中英文都搜**，年份用当前年。目标是穷尽「同类 + 可替代 + 邻域参考」，避免只盯一两个知名产品。

**查询模板**（按主题替换关键词）：

* `best {功能/品类} software` / `{品类} 软件 推荐 对比`
* `{品类} open source github` / `{品类} 开源 替代`
* `{已知竞品} alternatives` / `{已知竞品} 替代品`
* `{品类} reddit` / `{品类} 知乎 / V2EX 对比评测`
* `{品类} review G2 / Capterra / Product Hunt / AlternativeTo`

**形态全覆盖清单**（每类至少**搜**一次；无命中可空，勿编造）：

```
- [ ] 商业桌面/客户端软件
- [ ] 开源项目（GitHub / GitLab）
- [ ] SaaS / Web 应用
- [ ] 移动 App（iOS / Android）
- [ ] 浏览器插件 / IDE·CAD 插件
- [ ] CLI 工具 / 库 / SDK
- [ ] 间接替代（用别的方式解决同一痛点，如 Excel、手工流程）
```

**每个竞品记录字段**：

| 名称 | 形态 | 平台 | 商业模式·价格 | 开源? | 活跃度(最近更新) | 链接 | 一句话定位 |
|---|---|---|---|---|---|---|---|

价格、版本、星数等须核对来源；不确定标 **待验证**。

**数量**：主流 5–12 个列入清单；额外可标 1–2 个「小众强者」。**归类**：直接竞品 / 间接替代 / 邻域参考。

## 阶段 2：五维度分析（默认短写）

**结论**：默认用汇总表决策；禁止为形式完整给每个竞品写长优缺点（L0-01）。

对清单中的直接竞品（及必要时关键间接替代）按五维各打 **1–5 分**（1=差，5=优）。证据尽量来自官网/文档/真实用户评价；主观处标 **推断**。

**默认正文形态**：

1. 竞品清单表（阶段 1）
2. 汇总对比表（含加权总分 + 一行总评，总评含证据级别）
3. 行业现状小结（普遍好 / 普遍短板）各数句
4. **仅对加权总分前 3～5 个直接竞品**可各附极短优缺点（**各 ≤3 条**）
5. 其余竞品：清单一行即可，不堆同质段落

用户明确要求「详细 / 细致」时，再扩大优缺点篇幅。

**五维评估子项（rubric）**：

1. **功能（Functionality）**：核心覆盖、专业深度、边界能力、集成与扩展、平台广度。
2. **用户体验与易用性（UX & Usability）**：上手成本、界面与信息密度、高频效率、文档、本地化、无障碍。
3. **可靠与安全（Reliability & Security）**：数据安全/合规、认证权限、备份、可审计、漏洞响应。
4. **稳定性（Stability）**：崩溃与 Bug、大数据表现、资源占用、维护节奏、兼容性。
5. **差异化（Differentiation）**：独特卖点、护城河、价格模式、生态、数据可迁移、人群细分。

> 「差异化」评竞品时 = 相对其他产品的独特护城河；喂给阶段 3 找空白。

**汇总对比表**（加权总分 = Σ 各维得分 × 阶段 0 权重）：

| 竞品 | 功能 | 易用 | 可靠安全 | 稳定 | 差异化 | 加权总分 | 一句话总评（含证据级别） |
|---|---|---|---|---|---|---|---|

## 阶段 3：产品定义——该做什么样的软件

**结论**：从普遍短板与空白格反推定位；必须有差异化锚点与不做清单，避免更差的复制品。

1. **机会矩阵**：用户高频痛点 × 竞品满足度（高/中/低/空白）→ 圈空白/低满足 = 切入点。
2. **一句话定位**：为【目标用户】提供【核心价值】，区别于【主要竞品】在于【差异化锚点】。
3. **目标用户画像**：主要 + 次要（场景、痛点、当前替代）。
4. **MVP 功能集（MoSCoW）**——MoSCoW：Must / Should / Could / Won't，是按优先级切割范围的方法，作用是锁定最小可行产品（MVP，Minimum Viable Product，最小可行产品，作用是用最少功能验证价值）。

| 优先级 | 含义 | 功能 |
|---|---|---|
| Must | 没有它产品不成立 | … |
| Should | 重要但 MVP 后可补 | … |
| Could | 锦上添花 | … |
| Won't(now) | 本期明确不做 | … |

5. **非功能目标**：可量化（性能/可靠/安全/易用），对齐想超越的维度。
6. **差异化锚点**（≥1）：成本 / 体验 / 垂直 / 开放生态 / 可迁移 / AI / 工具链集成等。
7. **反向清单**：明确不做什么。

***

## 阶段 4：最优实现路径

**结论**：「最优」= 最小风险与成本、最快交付差异化；先构建方式，再技术细节；高风险须直接指出（L0-03）。

**① 构建方式决策**（优先复用，避免无脑自研）：

| 方式 | 适用 | 代价 |
|---|---|---|
| 从零自研 | 差异化在核心引擎、现有方案均不可复用 | 最高成本、最高可控 |
| Fork 成熟开源二次开发 | 已有接近底座，差异化在上层 | 省底座，受架构与许可约束 |
| 套用库/引擎/API 做壳 | 核心能力可被现成库/云 API 覆盖 | 最快，供应商/依赖锁定 |
| 现成 SaaS/低代码拼装 | 验证期、内部工具、非核心 | 最省力，定制与迁移受限 |

给出**推荐 + 理由**，并列 1 个备选。

**② 技术选型**：默认 + 备选；勿堆长串；核对**许可证**与商业用途。版本号须核对来源。

**③ 架构概要**：模块 / 数据流 / 风险点（一段话 + 必要时短列表，**不写实现代码**）。

**④ 路线图**：MVP → V1 → V2；每阶段交付物 + 验收点；最痛功能先做。验收点未实测标 **待验证**。

**⑤ 风险与对策**：

| 风险 | 类型(技术/许可/依赖/市场) | 影响 | 对策 |
|---|---|---|---|

**⑥ 假设验证**：最危险假设优先（原型、访谈、技术 PoC——Proof of Concept，概念验证，作用是低成本试通假设）。

## 阶段 5：落盘报告

**结论**：调研类产出进 Research，遵守项目文档结构；**不要**默认创建 `product-discovery/`。

1. **确定 `{DOCS}`**：仓库既有 `Docs/` 或 `docs/`；用户 `@` 了主题目录或已有多主题 → 用该主题下的 `{DOCS}`（如 `docs/FiniteElement/`）。
2. **目录**：`{DOCS}/Research/`（不存在则创建；**禁止**因此新增 `{DOCS}` 下第 6 个子目录）。
3. **序号**：扫描该 `Research/` 下现有 `编号-*.md`，取最大编号 +1；无文件时从 `01` 或与目录既有习惯一致的起始编号。
4. **文件名**：`{编号}-{主题}-YYYY-MM-DD.md`（日期用当天；对齐 L0-project-docs-structure / L0-05「项目文档结构优先」）。
5. **历史说明**：旧路径 `docs/product-discovery/` 或 `Docs/product-discovery/` **不再作为默认**；已有文件不强制本任务迁移。
6. 按下方模板写入；事实附来源链接；不确定标 **待验证**。
7. **先过「硬门禁」与文末自检**，通过后再落盘。

## 自检清单（落盘阻断）

下列任一项失败 → **禁止落盘**，先改正。自检内部完成，不向用户输出过程。

**写作硬门禁（L0-01/02/03）**

```
- [ ] 文首总论与各 ## 节有节首结论
- [ ] 术语/缩写首现已「是什么＋起什么作用」（含表格格）
- [ ] 关键结论已标 已验证/推断/建议/待验证；无未实测称「通过」
- [ ] 无「为填满模板」的空洞段落；未要求详细则篇幅以可判断取舍为限
```

**调研质量**

```
- [ ] 阶段 0 目标与五维权重已确认（缺省已标「假设」）；本轮提问≤3
- [ ] 竞品清单 ≥ 3 且搜索覆盖多种形态（不是清一色只搜一类）
- [ ] 有汇总对比表 + 加权总分 + 行业现状小结
- [ ] 头部 3～5 竞品有短评或分数依据；未对清单内每一项强制长优缺点
- [ ] 产品定义含「差异化锚点」与「不做清单」
- [ ] 实现路径先做了构建方式取舍（评估过 Fork/复用）
- [ ] 技术选型有默认+备选并核对许可证；版本/价格/路径已核对或标待验证
- [ ] 路线图最痛功能先做 + 最危险假设的验证手段；高风险已直指
- [ ] 竞品事实有来源链接，无编造
```

## 反模式（不要这样做）

* **用本 skill 模板完整度压过 L0-02** → 禁止落盘。
* **先落盘再补术语 / 节首结论** → 禁止。
* **每个竞品长文优缺点**（用户未要求详细）→ 禁止。
* **默认写入 `product-discovery/`** 或新增 `{DOCS}` 第 6 子目录 → 禁止。
* **报告或回复复述 rule 全文** → 禁止（审改规则时除外）。
* **跳过阶段 0** 直接搜竞品 → 方向跑偏。
* **只列功能、不打分、不对比** → 看不出差距与机会。
* **竞品只搜一种形态** → 漏掉开源/SaaS/插件强者。
* **产品定义没有差异化锚点** → 更差的复制品。
* **实现路径默认从零自研** → 未评估 Fork/复用。
* **模式 A 内直接写实现代码** → 越界；模式 B 允许改代码。
* **编造竞品、价格、用户数、测试通过** → 禁止；查不到标 **待验证**。
